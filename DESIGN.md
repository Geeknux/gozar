# Gozar

### Django-Bi-Admin

> Design document.
> Project name: **Gozar** — subtitle: *Django-Bi-Admin*.
> Status: M0 (skeleton), M1 (discovery + CRUD), M2 (semantic layer + query
> engine), i18n + per-user preferences, M3 (report UI) and M4 (access control +
> execution) done — see §10.
> Purpose of this file: the single source of context for starting implementation
> in a fresh session. Read it fully before writing code.

---

## 1. Vision

A from-scratch, installable Django app that replaces `django.contrib.admin` and
adds **deep, BI-grade reporting** plus a **natural-language report interface**:
a non-technical user types a request in plain language (Persian first, English
second) such as *"revenue for the last three months by city"* and gets a table,
chart, or dashboard — without knowing any table or field names.

### Positioning (why this exists)

Mature BI tools already exist (Metabase, Apache Superset, Redash). They connect
to the raw database and see only tables and columns. This project's edge is
that it **understands Django**:

- models, relations, choices, verbose names, managers, and custom querysets;
- Django's permission system, plus row-level rules defined in code;
- business logic expressed once in Python (a semantic layer), reused by the UI,
  the query engine, and the natural-language interface.

Secondary differentiators, weak in existing tools:

- **First-class Jalali (Solar Hijri) calendar**: grouping, filtering, and
  relative periods computed in the database, not just at display time.
- **Proper RTL UI** with Persian digits and locale-aware number formatting.

### Non-goals (for v1)

- Not a general BI tool for non-Django databases.
- Not a CMS / page builder.
- No arbitrary SQL generated by an LLM (see §6).
- No multi-database federation in v1.

## 2. Background decisions (already made)

1. **Stay on Python/Django.** Rewriting Django itself in Rust is not justified;
   the value of Django is development speed and its dynamic introspection.
   Rust may later be used only for measured hot paths (via PyO3/maturin), and
   Granian (Rust ASGI server) is an acceptable deployment option.
2. **Build on the ORM, not raw SQL.** The query engine compiles a structured
   report spec into Django ORM querysets, so permissions, managers, and
   row-level rules apply automatically and SQL injection is structurally ruled
   out.
3. **The LLM never writes SQL.** It produces a structured `ReportSpec` (JSON)
   constrained to the semantic layer's catalog; the spec is validated and then
   executed by the same engine the GUI uses.
4. **Semantic layer is the core asset.** Quality of the NL interface depends far
   more on good labels/synonyms/descriptions than on the model used.

## 3. Architecture overview

```
┌──────────────────────────────────────────────────────────────────┐
│ Frontend (SPA: React or Vue)  — RTL, Jalali, ECharts, data grid  │
└───────────────▲──────────────────────────────────────────────────┘
                │ JSON API (DRF or django-ninja)
┌───────────────┴──────────────────────────────────────────────────┐
│ 1. Model discovery   — introspect apps/models/fields/relations   │
│ 2. Semantic layer    — dimensions, measures, labels, synonyms    │
│ 3. Query engine      — ReportSpec → validated → Django ORM       │
│ 4. Execution layer   — async jobs, replica routing, cache        │
│ 5. Access control    — Django perms + row-level rules            │
│ 6. NL interface      — text → ReportSpec via LLM structured out  │
└───────────────┬──────────────────────────────────────────────────┘
                │
        Primary DB (writes) / Read replica (reports) / optional DuckDB|ClickHouse
```

### 3.1 Model discovery

- Walk `django.apps.apps.get_models()`; for each model read `_meta`:
  fields, internal types, `choices`, `verbose_name`, nullability, FK/M2M/reverse
  relations, `related_model`.
- Build a **relation graph** so users can traverse `Order → Customer → City`.
- Output: an in-memory registry (cached; rebuilt on startup / app reload).
- Drives the auto-generated CRUD (the "replace contrib.admin" part).

### 3.2 Semantic layer

Declared in Python by developers, registered per model. Concepts:

- **Dimension**: a groupable/filterable attribute (field or lookup path, or an
  expression). Has type (`time`, `category`, `number`, `boolean`, `geo`).
- **Measure**: a named aggregation with business logic baked in.
- **Labels / synonyms / descriptions**: in Persian and English; these are the
  primary context for the NL interface.
- **Default time dimension** per semantic model.

Sketch:

```python
from django.db.models import Sum, Count, Avg, Q
from bi_admin.semantic import Semantic, Dimension, Measure, register


@register
class OrderMetrics(Semantic):
    model = Order
    time_dimension = "created_at"

    dimensions = {
        "created_at": Dimension(
            "created_at", type="time", label={"fa": "تاریخ ثبت سفارش", "en": "Order date"}
        ),
        "paid_at": Dimension(
            "paid_at", type="time", label={"fa": "تاریخ پرداخت", "en": "Payment date"}
        ),
        "city": Dimension(
            "customer__city__name",
            type="category",
            label={"fa": "شهر", "en": "City"},
            synonyms={"fa": ["استان", "محل"]},
        ),
        "status": Dimension("status", type="category"),
    }

    measures = {
        "revenue": Measure(
            Sum("amount", filter=Q(status="paid")),
            label={"fa": "درآمد", "en": "Revenue"},
            synonyms={"fa": ["فروش", "گردش مالی", "دریافتی"], "en": ["sales"]},
            description={
                "fa": "جمع مبلغ سفارش‌های پرداخت‌شده",
                "en": "Sum of amounts of paid orders",
            },
            format="currency",
        ),
        "orders": Measure(Count("id"), label={"fa": "تعداد سفارش", "en": "Orders"}),
        "aov": Measure(Avg("amount"), label={"fa": "میانگین سبد", "en": "Avg order value"}),
    }
```

### 3.3 Query engine

Input: a `ReportSpec`. Output: rows + column metadata.

Responsibilities:

- Validate every measure/dimension/filter against the semantic catalog.
- Compile to ORM: `.filter()`, `.annotate()`, `.values()`, aggregation,
  `Trunc*` for time grains, `Window` functions (running totals, rank, share of
  total, period-over-period), subqueries.
- Apply access control (see 3.5) **inside the engine**, never in the UI.
- Enforce limits: max rows, max dimensions, statement timeout.
- Drill-down: given a cell (dimension values), return the underlying records
  queryset.

`ReportSpec` (pydantic, also the LLM output schema):

```python
from typing import Literal
from pydantic import BaseModel


class Filter(BaseModel):
    field: str  # dimension key
    op: Literal["eq", "neq", "in", "not_in", "gte", "lte", "between", "contains", "is_null"]
    value: str | int | float | bool | list | None = None


class Sort(BaseModel):
    field: str  # measure or dimension key
    direction: Literal["asc", "desc"] = "desc"


class ReportSpec(BaseModel):
    semantic_model: str
    measures: list[str]
    dimensions: list[str] = []
    filters: list[Filter] = []
    time_dimension: str | None = None  # defaults to model's
    time_grain: Literal["day", "week", "month", "season", "year"] | None = None
    calendar: Literal["jalali", "gregorian"] = "jalali"
    relative_period: str | None = None  # e.g. "last_3_months", "last_year",
    # "this_season" — resolved in code
    compare_to: Literal["previous_period", "same_period_last_year"] | None = None
    sort: list[Sort] = []
    limit: int | None = 1000
    chart: Literal["table", "bar", "line", "area", "pie", "pivot", "kpi"] = "table"
    clarification_needed: str | None = None  # set by the LLM when ambiguous
```

Optional raw-SQL mode for power users only: read-only DB role, separate
connection alias, `SET statement_timeout`, row limit, audited.

### 3.4 Execution layer

- Heavy reports run as background jobs (Celery, or the Django tasks framework
  if available in the chosen Django version); the UI polls or receives push
  updates.
- Database router sends report queries to a read replica when configured.
- Result cache keyed by (normalized spec, user's row-level scope, data version).
- Pre-aggregation: materialized views / summary tables for hot reports.
- Later: optional columnar engine (DuckDB to start, ClickHouse at scale) fed by
  periodic sync; the engine picks the backend per semantic model.

### 3.5 Access control

- Model-level: reuse Django permissions (`view_*`).
- Semantic-level: per measure/dimension visibility (e.g. hide `margin`).
- Row-level: pluggable rules, e.g.
  `rule(OrderMetrics, lambda user: Q(branch=user.profile.branch))`.
- Applied in the query engine for GUI, API, NL, and drill-down alike.
- Audit log of every report execution (user, spec, duration, row count).

### 3.6 Frontend

- SPA (React + TypeScript, Vite) served by Django.
- Components: auto CRUD lists/forms, report builder (pick measures/dimensions/
  filters), pivot table, charts (ECharts), dashboards (grid of widgets with
  global filters), drill-down, export (XLSX/CSV), scheduled email reports.
- RTL-first layout, `dir="auto"` on user-generated text, Persian digits, Jalali
  date pickers.
- Data grid candidates: AG Grid (community) or TanStack Table.

## 4. Jalali calendar requirements

- Grouping by Jalali month/season/year **must happen in the database**: Jalali
  months do not align with Gregorian months, so converting after aggregation is
  wrong.
- Approach options (evaluate in milestone 2):
  1. A calendar dimension table (one row per day: gregorian date, jalali
     y/m/d, season, week, holiday flags) joined on date — portable and fast.
  2. DB functions (PostgreSQL SQL/PLpgSQL function for jalali conversion)
     exposed as Django `Func` expressions.
- Prefer option 1 (also enables holidays/working days in reports).
  **Decided in M2: option 1** (`bi_admin.CalendarDay`, see §10).
- Relative periods ("last year", "this season", "last 3 months") resolve in
  deterministic Python code against today's Jalali date — never by the LLM.
- Library for Python-side conversion: `jdatetime` (verify current status).

## 5. Natural-language interface

### 5.1 Pipeline

```
user text (fa/en)
  → retrieve relevant catalog entries (embeddings over labels/synonyms/descriptions)
  → LLM call with structured output (ReportSpec JSON schema)
  → validate against semantic layer
      ↳ invalid: send errors back to LLM, retry (max 2)
      ↳ clarification_needed: ask the user, stop
  → resolve relative dates + match category values (fuzzy/value index)
  → render human-readable interpretation ("Paid revenue by city, 1 Tir → today")
  → execute via query engine (same perms) → table/chart
```

### 5.2 Prompt context

- Semantic catalog subset (keys, labels, synonyms, descriptions, types).
- Today's date in both calendars.
- Few-shot examples (curated + learned from user corrections).
- Previous `ReportSpec` when the user is refining ("now only Tehran",
  "make it monthly") — the model edits the spec rather than starting over.

### 5.3 Hard problems to handle

- **Value matching**: user writes "تهران", DB has "Tehran" or a variant. Keep
  a distinct-values index per category dimension; fuzzy + transliteration +
  optional embedding match.
- **Ambiguity**: multiple time dimensions, overlapping measure names → ask.
- **Large schemas**: never dump the whole catalog; retrieve top-k.
- **Explainability**: always show the interpretation sentence and let the user
  adjust via normal filter UI.

### 5.4 Provider abstraction & privacy

- Only the catalog and the user's text go to the LLM — never row data.
- Use an OpenAI-compatible client interface so hosted models and local
  servers (Ollama, vLLM) are interchangeable via settings.
- Cache NL → spec results; log prompts/outputs for evaluation (opt-in).

### 5.5 Evaluation

- Golden set: ≥100 real Persian (and some English) questions with expected
  `ReportSpec`s, stored as fixtures; run in CI against a stub or real model.
- Metrics: exact/semantic spec match rate, clarification rate, retry rate.
- Every user correction becomes a candidate golden example + few-shot.

## 6. Security principles

1. No LLM-generated SQL, ever. LLM output is data (a spec), validated.
2. Access control lives in the query engine.
3. Raw SQL mode: opt-in, read-only role, timeout, row limit, audited.
4. Resource limits on every query (timeout, row cap, dimension cap).
5. Exports respect the same row-level scope.
6. Secrets (LLM keys, DB credentials) only via settings/env.

## 10. Decisions & open questions

Decided (M0, 2026-10-18):

- Frontend: **React + TypeScript** (Vite).
- API: **django-ninja** — `ReportSpec` doubles as API schema and LLM output schema.
- Minimum versions: **Django 5.2 LTS, Python 3.12, PostgreSQL 16**.
- Tests run on SQLite by default; CI also runs PostgreSQL 16
  (`GOZAR_DB=postgres`). Jalali/DB-function work in M2 targets PostgreSQL.
- Distribution name `gozar`, import package `bi_admin`.

Decided (M1, 2026-10-18):

- License: **MIT**.
- Discovery (`bi_admin.discovery`): lazily built, process-wide `Registry` of
  `ModelInfo`/`FieldInfo`/`RelationInfo` read from `_meta`; relations are
  stored in both directions with a `many` flag; `find_path` (BFS, to-one hops
  first) and `resolve_lookup` (validates `a__b__c` paths) are the building
  blocks M2's validator will reuse. Hidden by default: contenttypes, sessions,
  admin, bi_admin, `auth.permission`; tune with `GOZAR["INCLUDE_APPS"|
  "EXCLUDE_APPS"|"EXCLUDE_MODELS"]`.
- CRUD (`bi_admin.crud`): `ModelOptions` mirrors the core of `ModelAdmin`
  (`list_display` incl. lookup paths and callables, `search_fields` with
  `^ = @`, `list_filter`, `ordering`, `fields`/`exclude`/`readonly_fields`,
  `list_per_page`, actions, permission and save/delete hooks), registered via
  `@register(Model)` in an app's auto-discovered `gozar.py`. Defaults are
  derived from `_meta`. Validation goes through a generated `ModelForm`.
- Permissions: staff session + CSRF on every endpoint; Django `view/add/
  change/delete` perms (change implies view); deletion also requires delete
  permission on every cascaded registered model, and PROTECT/RESTRICT returns a
  409 with the blocking objects. Filters/ordering accept only declared paths, so
  a filter can't be used as an oracle on hidden fields (e.g. password hashes).
  Password fields are write-only and hashed with `set_password`.
- History: `bi_admin.ChangeLog` (add/change/delete with changed field names),
  the counterpart of admin's `LogEntry`. *(M4 kept the report audit log in its
  own model, `ReportLog`.)*
- Search normalises Arabic ي/ك to Persian ی/ک (and back) per term.
- UI: React SPA built by Vite into `bi_admin/static/bi_admin/spa/` (git-ignored,
  shipped as a wheel artifact); Django serves the shell (`bi_admin.views.spa`)
  via the Vite manifest. Dates are shown in Jalali via `Intl`
  (`fa-IR-u-ca-persian`), numbers with Persian digits. Date inputs are still
  Gregorian browser pickers — Jalali pickers come with M3. *(Superseded by the
  i18n decisions below: English/Gregorian are now the defaults.)*

Decided (M2, 2026-10-18):

- Semantic API (`bi_admin.semantic`): subclass `Semantic` (`model`, optional
  `name`, `label`, `synonyms`, `description`, `time_dimension`, `dimensions`,
  `measures`) and decorate with `@register` in an app's `gozar.py`. The key in
  `ReportSpec.semantic_model` defaults to the snake-cased class name
  (`OrderMetrics` → `order_metrics`). Models bind lazily: dimension paths are
  checked with `Registry.resolve_lookup`, measure expressions are resolved
  against the model without querying; mistakes raise `ImproperlyConfigured` and
  surface as system check `bi_admin.E001`. Labels/descriptions normalise to
  `{"fa", "en"}` (a bare string is Persian; defaults come from verbose names),
  synonyms to per-language lists. Dimension `type` is inferred from the field
  (date/datetime → time, numbers → number, boolean, otherwise category);
  expression dimensions need an explicit type. `hidden=True` keeps an item out
  of the catalog and the validator. `catalog(lang, request)` lists what a user
  may report on.
- Permissions: `Semantic.has_permission` defaults to the CRUD view permission
  of the model (change implies view) and `get_queryset` to the CRUD options'
  queryset, so reports and CRUD see the same rows. M4 adds row-level rules on
  top of `get_queryset` (see the M4 decisions).
- `ReportSpec` (`bi_admin.engine.spec`) is the §3.3 model with
  `extra="forbid"`. Filter values for time dimensions are dates, Gregorian
  (`2026-03-21`) or Jalali (`1405/01/01`, any year below 1700), Persian digits
  allowed; a category value may be its choice label (`پرداخت‌شده` → `paid`).
- Validator (`bi_admin.engine.validate`) collects every problem into
  `SpecError(code, message, path, value, suggestions)`; suggestions match keys,
  labels and synonyms (Arabic ي/ك normalised) and then fuzzy matches. Codes:
  `unknown_semantic_model`, `unknown_measure`, `not_a_measure`,
  `unknown_dimension`, `not_a_dimension`, `invalid_lookup`, `duplicate`,
  `no_measures`, `too_many_dimensions`, `no_time_dimension`,
  `not_a_time_dimension`, `unknown_relative_period`, `invalid_operator`,
  `invalid_value`, `invalid_choice`, `measure_filter_not_supported`,
  `sort_field_not_in_report`, `unknown_field`, `invalid_limit`,
  `limit_exceeded`, `not_supported` (`compare_to`, until M6) and
  `clarification_needed`. Caps: `GOZAR["REPORT_MAX_ROWS"]` (10 000; also the
  limit when `limit` is null) and `GOZAR["REPORT_MAX_DIMENSIONS"]` (6).
  Filtering on measures (HAVING) is deferred.
- Time semantics: `time_grain` adds the time dimension (spec's or the model's
  default) as the first group key; any time dimension listed in `dimensions` is
  bucketed too (grain defaults to `day`). Null times form a null bucket, sorted
  last. All date logic uses local dates in `TIME_ZONE`; date filters and
  periods compile to half-open aware datetime ranges so indexes still apply.
  Default order: chronological when bucketed, else first measure descending;
  remaining group keys always break ties so `LIMIT` is deterministic.
- Jalali grouping: calendar dimension table `bi_admin.CalendarDay` (one row per
  day: Gregorian y/q/m/d, ISO week, Jalali y/season/m/d, Saturday-based Jalali
  weekday, `*_start` dates of the enclosing week/month/season/year in both
  calendars, `is_weekend` (Friday; `GOZAR["WEEKEND_DAYS"]`), `is_holiday` +
  `holiday_name` for the fixed solar holidays — lunar holidays move every year
  and must be added per row). The compiler groups by a correlated lookup
  `(SELECT jalali_month_start FROM bi_admin_calendarday WHERE date =
  local_date(created_at))`; Django groups by select position on SQLite and
  PostgreSQL, verified on both. Gregorian grains use `Trunc*` (ISO weeks start
  Monday; `season` = calendar quarter) and need no table. A Jalali query whose
  dates the table doesn't cover fails with `409 calendar_not_populated` rather
  than returning null buckets. `manage.py gozar_calendar [--start] [--end]
  [--clear]` fills it (default: 15 Jalali years back to the end of the year 5
  ahead; idempotent; keeps edited rows). The per-row lookup is a PK probe; if it
  shows up in profiles, M4/M7 can denormalise a date key or pre-aggregate.
- Result shape: a bucket's value is its Gregorian start date (ISO) plus a
  neutral label in `<key>__label` (`1405-07`, `1405-S3`, `1405`, `2026-W42`,
  `2026-Q4`); the UI formats month/season names. Decimals become ints when
  integral (within 2^53), otherwise floats. The response carries `columns`
  (role, type, fa/en label, grain, calendar, choices, format), `rows`,
  `truncated`, the normalised `spec` and the resolved `period`.
- Relative periods (`bi_admin.calendar.periods`): `today`, `yesterday`,
  `this_<unit>` (to date), `last_<unit>`, `last_<N>_<unit>s` (N complete units
  before the current one) and `past_<N>_<unit>s` (current unit to date plus the
  N-1 before it); units day/week/month/season(=quarter)/year; in the spec's
  calendar; resolved against `periods.today()` (= `timezone.localdate()`, which
  tests monkeypatch).
- API: `GET /api/reports/catalog?lang=fa|en`, `POST /api/reports/validate`,
  `POST /api/reports/run` — staff session + CSRF like CRUD; `403
  permission_denied` without the model's view permission, `422` with structured
  errors for an invalid spec (pydantic's own 422 for schema errors). Suggestions
  for an unknown semantic model only list models the user may see.
- Demo `OrderMetrics` (`example_project/shop/gozar.py`) follows §3.2, plus
  `province`, `customer` and `amount` dimensions and `paid_orders`/`customers`
  measures. Two deliberate changes from the sketch: `aov` averages paid orders
  only (consistent with `revenue`), and the synonym "استان" moved from `city` to
  the new `province` dimension.

Decided (i18n + preferences, 2026-10-18):

- **English is the source language and the default; Gregorian is the default
  calendar.** Persian and Jalali stay fully supported as per-user choices.
  This revises the Persian-first framing of §1 for the UI: the product is
  bilingual, and Persian is still first-class (RTL, digits, Jalali in the DB).
- Backend strings use gettext: error messages, the CRUD "Delete selected"
  action, `ChangeLog` fields and action choices, `CalendarDay` and
  `UserPreferences` verbose names, the SPA shell template. The Persian catalog
  lives in `src/bi_admin/locale/fa/LC_MESSAGES/` with the compiled `.mo`
  committed (CI needs no gettext tools); regenerate with `django-admin
  makemessages -l fa` + `compilemessages` from `src/bi_admin`. The demo shop
  does the same in `example_project/shop/locale/`. Verbose names follow the
  Django convention (lower-case English, e.g. `order`); `path_label` and
  semantic fallbacks capitalise them, the SPA capitalises headings.
- Demo seed data (2026-10-19): `seed_demo` writes English names by default —
  real Iranian cities with English city and province names (Tehran / Tehran,
  Mashhad / Razavi Khorasan, …), English customer names (Ali Karimi, …) and
  product names (Saffron 5 g, …). `--locale fa` writes the Persian data set for
  RTL demos and the Arabic ك/ي → Persian ک/ی search normalisation. `City.name`
  is in the chosen locale and `City.name_en` is always English. The data sets
  are parallel tables drawn by the same random calls, so a given `--seed`
  produces identical orders, amounts, dates, phones and cities in both locales;
  only the names differ (a test asserts this). Tests use the English set
  (`seeded` fixture) and the Persian one where it matters (`seeded_fa`, e.g.
  Arabic kaf/yeh search, Persian autocomplete).
- The discovery registry is cached **per active language**, since verbose names
  and choice labels are translated when it is built. Semantic models bind once
  and compute both languages up front (`in_languages`): default labels come
  from verbose names, a bare-string label/description is English source text
  run through gettext (so `gettext_lazy("Revenue")` works), dimension choices
  carry `{"fa", "en"}` labels and the validator accepts a choice label in
  either language.
- Preferences: `bi_admin.UserPreferences` (one row per user: `language` en|fa,
  `calendar` gregorian|jalali, both blank = project default, plus an `options`
  JSON object for later settings). Defaults: `GOZAR["DEFAULT_LANGUAGE"]` and
  `GOZAR["DEFAULT_CALENDAR"]` (fallback en / gregorian; unsupported values
  fall back too). Reading never creates a row.
- `bi_admin.middleware.PreferencesMiddleware` (after `AuthenticationMiddleware`)
  replaces `LocaleMiddleware`: staff users get their stored language, anonymous
  requests the `django_language` cookie or `Accept-Language` when supported,
  else the project default. It sets `Content-Language`, varies on
  `Accept-Language`/`Cookie`, and restores the previous thread language after
  the response so nothing leaks into the next request.
- API: `GET /api/preferences` and `PATCH /api/preferences` (partial; `null`/`""`
  resets a field; options are merged; 400 with per-field errors; the response is
  already in the new language). `/auth/me` and the login response include
  `preferences`. Same staff session + CSRF as the rest of the API; no model
  permission is needed to set one's own preferences.
- Reports: `ReportSpec.calendar` now defaults to `null` and resolves to the
  spec's value → the user's calendar → `GOZAR["DEFAULT_CALENDAR"]`; the
  response's `spec.calendar` shows the resolved one. `periods.resolve` defaults
  to Gregorian. Report column metadata has `label` in the user's language plus
  `labels` with both; `GET /api/reports/catalog` returns the user's language by
  default (`lang=fa|en` overrides, `lang=all` returns both). Validation
  messages are translated; error `code`s never change.
- SPA: `frontend/src/i18n/` holds the `en` and `fa` dictionaries (`fa` is typed
  against `en`, so a missing key fails `tsc`) and a small context
  (`useI18n()` → `t`, `fmt`, `cap`, `lang`, `calendar`, `dir`); no new
  dependency. `fmt` formats numbers and dates with `Intl`
  (`en-US`/`fa-IR`, `-u-ca-gregory|persian`, Latin or Persian digits). The
  Settings page (top bar → Settings) saves each change at once and applies it
  immediately: `<html lang dir>`, digits, dates, and a remount of the routes so
  pages refetch server-translated metadata. Before login the page follows the
  server's choice (browser / project default) and offers an English/فارسی
  switch that sets the `django_language` cookie.

Decided (M3 — report UI, 2026-10-19):

- Reports area at `/reports` (sidebar), lazy-loaded so ECharts (~580 kB) only
  loads there. Builder on the side, results beside it; on narrow screens they
  stack. Everything is driven by `GET /reports/catalog` (in the user's
  language).
- **The URL is the state**: the builder edits a `ReportSpec` serialised as
  `?spec=<json>` (empty/default keys dropped), so reports are shareable and
  reloadable; "Copy link" copies it. Saved reports in the database are left
  for M6 (dashboards), where they are needed anyway.
- Live editing: every change is validated (`POST /reports/validate`, 350 ms
  debounce) and, when valid, run. Half-filled filters are left out of the
  request (and error paths are mapped back to the original filter rows), so
  adding a filter doesn't flash errors. Errors render next to their section by
  `path` (`measures[0]`, `filters[2].value`, `limit`, …), with suggestions
  shown by label. Changing only the chart type never re-queries.
- Time controls: date field, grain, calendar ("my calendar" = the user's
  preference, or force Gregorian/Jalali), and a period that is either a
  relative period preset or a custom range. The custom range is stored as a
  `between` filter on the time dimension (no new spec field) and shown in the
  time section instead of the filter list.
- Filter value pickers: `GET /reports/values` returns a dimension's values —
  its choices (labels in the user's language), related objects searched with
  the target's `search_fields` (the CRUD autocomplete rules, Arabic/Persian
  letters included) when the path ends on a relation, otherwise distinct
  values from the semantic queryset (`icontains`, limit 50). Time dimensions
  use the date picker; numbers a text input (Persian digits accepted).
- Results: a client-side sortable table (dimension values formatted —
  time buckets as "Oct 2026" / "مهر ۱۴۰۵", "Q4 2026" / "پاییز ۱۴۰۵", choices by
  label; measures by their `format`: currency/integer without decimals,
  percent as %, decimal with 2), bar/line/area/pie (ECharts), pivot (exactly
  two group-by fields; rows × columns of one measure) and KPI cards (no
  group-by). Charts plot one measure at a time (a selector appears when there
  are several, so scales don't clash); a second group-by field becomes the
  series. ECharts gets the user's digits and compact number format on axes,
  bucket labels in the report's calendar, the page font, and in RTL a
  reversed category axis, the value axis on the right and right-aligned
  legends. Unsuitable chart/shape combinations show a hint instead of a broken
  chart. The pivot has no totals column: totals of non-additive measures
  (averages, distinct counts) can't be derived client-side; M6 may add server
  totals.
- Drill-down (`POST /reports/drilldown` → `bi_admin.engine.drilldown`): the
  clicked group values become extra filters on the spec — a time bucket becomes
  a `between` covering the bucket (it must start a bucket of that grain in the
  report's calendar), `null` becomes `is_null` — and the narrowed spec goes
  through the normal validator and compiler, so lookups, coercion, choice
  labels, the semantic `get_queryset` and permissions are identical to the
  report. Clicking a measure also applies that aggregate's own `filter=Q(...)`
  (revenue → paid orders), so record counts match the cell for count-like
  measures (tests assert this for every cell of a report). Errors point at
  `cell.<key>` / `measure`. Rows are serialised like the CRUD list (its
  `list_display`, ordering, `select_related`), paginated (25, max 200), and
  link to the CRUD detail pages; `.distinct()` when a filter crosses a
  to-many relation.
- Export (`POST /reports/export?format=csv|xlsx`): runs the spec through the
  same `run()` (permissions, limits) and writes the result with headers in the
  user's language, bucket labels for time columns and choice labels for
  choices. CSV is UTF-8 with a BOM (spreadsheet apps detect Persian text);
  XLSX (openpyxl, new dependency) has a bold frozen header, number formats per
  measure format and a right-to-left sheet for Persian users. The SPA
  downloads via `fetch` + blob (POST with CSRF).
- Date picker (`components/DatePicker.tsx`): a dependency-free month grid in
  the user's calendar (Jalali weeks start Saturday, Gregorian Monday), values
  always Gregorian ISO dates. Gregorian→Jalali uses `Intl`'s Persian calendar;
  Jalali→Gregorian starts from an estimate and corrects with `Intl`
  (round-trip verified for every day 1990–2040). Used in the report builder,
  the CRUD list date filters and the CRUD form (date fields, and date + time
  for datetime fields), replacing the native Gregorian inputs.

Decided (M4 — access control & execution, 2026-10-19):

- Settings: every `GOZAR` key and its default lives in `bi_admin/conf.py`
  (`setting(name)`); the validator's caps moved there too.
- **Row-level rules** (`bi_admin.access.rules`): a rule is a callable taking the
  *user* (not the request, so background jobs evaluate it identically) and
  returning a `Q`, `True`/`None` (no restriction) or `False` (no rows). Declared
  with `rule(target, fn)` / `@rule(target)` — target a model, an `"app.model"`
  label or a `Semantic` — or as `row_rules = [...]` on `ModelOptions` /
  `Semantic`. All applicable rules are AND-ed: model rules apply to that model's
  CRUD, to every relation picker listing it and to every semantic model over it;
  semantic rules add to those for reports only. They are applied *outside* the
  overridable hooks: `model_queryset(options, request)` =
  `options.get_queryset` + rules, `semantic_queryset(sem, request)` =
  `Semantic.get_queryset` + model rules + semantic rules, so a custom
  `get_queryset` can't drop them. Evaluated once per request (memoised on it).
  Fail closed: a rule that raises or returns something else denies every row
  (logged). Superusers bypass rules unless `ROW_RULES_BYPASS_SUPERUSER = False`.
  `request=None` (trusted code, e.g. `run(spec)` in a shell) is unrestricted.
- Every path is scoped: report run, drill-down, export, value lookups (distinct
  values from the scoped semantic queryset; relation values from the target
  model's scoped queryset), jobs; CRUD list (and its unfiltered total), filter
  choices, detail, update, delete, history, autocomplete, actions (the selection
  is intersected with the scope) and delete plans. Writes: relation form fields
  only accept rows in scope — plus the ones already linked, so editing other
  fields never fails on a hidden link — and a save whose row would end up outside
  the scope is rolled back with `403 out_of_scope`. A delete whose cascade would
  reach rows outside the user's scope is refused (`out_of_scope` in the plan,
  `409` on delete); protected-object samples never name hidden rows. `validate`
  touches no rows, so only visibility applies there. Known gap: M2M values on a
  detail page still list every linked object.
- **Semantic visibility**: `Dimension`/`Measure` take `permission=` — a
  permission name, a list (all required) or a predicate on the user (a failing
  predicate hides the item). `Semantic.is_visible(item, request)` is the hook;
  `visible_dimensions/measures(request)` and `default_time_dimension(request)`
  build on it, and the catalog, validator (hence run, drill-down, export, jobs)
  and value lookups use them, so a hidden key gets exactly the error and
  suggestions an unknown one would (`unknown_measure`, `unknown_dimension`,
  `unknown_field` in sort — never `sort_field_not_in_report`); suggestions and
  synonym matches never reveal it. A hidden default time dimension behaves as
  none. Superusers pass permission strings (they have every permission), but
  predicates decide for everyone. Drill-down drops list columns whose path (or
  a relation leading to it) is read only by items the user can't see — paths of
  invisible items minus paths of visible ones (`Semantic.hidden_fields`), using
  the dimension paths and the measures' aggregated fields (not their `filter=`).
  `hidden=True` still means "internal", not a permission. Demo: *Refunds*
  needs `shop.change_order`.
- **Audit log**: new model `bi_admin.ReportLog` (user + username copy, kind
  run/export/drilldown, semantic model, normalised spec — the resolved calendar
  included — scope, status ok/invalid/denied/failed, error code and message,
  duration, row count, cache hit, database, job). Written by
  `access.audit.record()` around every execution in the engine, so API, jobs
  and code with a request are covered, including refused (403 → `denied`),
  invalid (422 → `invalid`, first error code) and failed ones (timeouts,
  `calendar_not_populated`, `internal_error`). `validate` and value lookups
  aren't executions and aren't logged; exporting a finished job's stored result
  is. The scope column is the WHERE clause of the user's scoped base queryset
  (`""` = all rows), which also captures custom `get_queryset` filters. The
  insert runs in its own savepoint and never masks the report's own outcome;
  `AUDIT_REPORTS = False` turns it off. Readable with the model's view
  permission `bi_admin.view_reportlog` (the model has no add/change/delete
  perms) through `GET /api/audit/reports` (filters user, status, kind,
  semantic_model, error_code, `q`; paginated) and the SPA's **Audit log** page;
  `/auth/me` returns `permissions.audit`. `ChangeLog` was not extended: it
  records object edits keyed by model/pk, a different shape and audience.
- **Limits**: `REPORT_MAX_ROWS` (10 000), `REPORT_MAX_DIMENSIONS` (6, the time
  grain counts) and the new `REPORT_MAX_FILTERS` (20 → `too_many_filters`) are
  validator errors (422). `REPORT_STATEMENT_TIMEOUT_MS` (30 000; 0 = off) wraps
  every report, drill-down and value query (`execution.limits`): PostgreSQL runs
  them in a transaction with `set_config('statement_timeout', ms, true)` (=
  `SET LOCAL`), restoring the previous value afterwards because a savepoint
  inside an outer transaction would otherwise keep it, and maps SQLSTATE 57014;
  SQLite installs a progress handler (every 1000 VM steps) that interrupts the
  statement past the deadline; other backends run unlimited. Both map to `504
  statement_timeout` with `timeout_ms`.
- **Result cache** (`execution.cache`, Django's cache framework, alias
  `REPORT_CACHE`, `REPORT_CACHE_TIMEOUT` = 300 s, 0 = off; on by default). Key =
  SHA-256 of the normalised spec without `chart` (chart switches share an
  entry), the resolved period, an exact scope fingerprint (the scoped base
  queryset's SQL with typed params — `str(query)` inlines params unquoted, so it
  is only used for display), the language (column labels), the reports database
  and the data versions. Dependencies are read off the compiled SQL: every
  model whose quoted table name appears (joins, subqueries such as the
  calendar lookup or a rule's `__in` subquery) plus the semantic model's own.
  A data version is a random token per model (plus a global epoch for
  `bump_all()`), replaced on `post_save`/`post_delete`/`m2m_changed` — at once
  (the writer's own transaction) and again `on_commit` (a reader that cached
  pre-commit data in between is invalidated). A missing (evicted) version gets
  a new random token, so it can't resurrect old entries. Receivers are
  connected per model, skipping Gozar's bookkeeping and Django's plumbing, so
  those keep Django's fast bulk delete. Bulk writes send no signals:
  `cache.bump(Model)` is called by CRUD actions, `gozar_calendar` and
  `seed_demo`. Permission and validation always run before the lookup; errors
  are never cached. The run response has `cache: {enabled, hit, stored_at}`;
  `?cache=false` on run/export/jobs bypasses the lookup but stores the fresh
  result; the SPA's **Refresh** does that. The cache must be shared across
  processes for the worker's results to be reused — the demo uses
  `FileBasedCache` in `example_project/.cache` (tests: `LocMemCache`).
- **Read-replica routing** (`execution.router`): `reporting(alias)` sets a
  context variable while report, drill-down, export and value-lookup queries
  run; `ReportsRouter.db_for_read` returns it, and the engine also passes the
  alias explicitly (`QuerySet.using`), so the main queries are routed even
  without the router. CRUD reads, all writes, permission/preference reads, the
  audit log and jobs stay on `default`. Checks: `bi_admin.E002` (alias not in
  `DATABASES`), `bi_admin.W001` (router not installed). The demo defines a
  `replica` alias (same SQLite file in development, a separate test database —
  `test_gozar_replica` on PostgreSQL — in tests); `GOZAR_REPORTS_DATABASE=replica`
  enables it. Cache entries are per database.
- **Background jobs** (`execution.jobs`): model `bi_admin.ReportJob` (UUID pk,
  owner, spec, options = submitter's language/calendar/cache flag, status
  queued/running/done/failed/cancelled, timestamps, result JSON = the `/run`
  body, error payload + HTTP status). Synchronous by default; async when
  `?mode=async`, or `mode=auto` (default) and `Semantic.run_async` /
  `REPORT_ASYNC` say so; `mode=sync` forces it. Submitting validates first
  (403/422 come back at once, no job) and returns a cached result directly
  (`200`); otherwise `202 {"job"}`. Endpoints `POST /reports/jobs`, `GET
  /reports/jobs`, `GET /reports/jobs/{id}`, `/result` (the run body; `409
  job_not_finished`, `410 job_cancelled`, or the failure with the status a
  synchronous run would have had), `POST /{id}/cancel`, `GET /{id}/export`
  (from the stored result, no new query). Jobs are private: another user's job
  is a `404 job_not_found`. Pluggable `JOB_BACKEND` with `submit(job)`:
  `DatabaseBackend` (default; nothing to do, `manage.py gozar_worker [--burst]
  [--sleep] [--max-jobs] [--keep-days 7]` claims jobs) and `ImmediateBackend`
  (runs inside the request; tests and development). A worker claims with a
  conditional `UPDATE … WHERE status='queued'` (portable, no `SKIP LOCKED`
  needed) and runs the job as the owner with a request stand-in
  (`JobRequest`) in their language, so permissions, visibility and rules are
  re-checked at execution time (a user who lost access gets a failed job with
  403). A job cancelled while running stays cancelled. Finished jobs older
  than `--keep-days` are purged. Not handled yet: requeueing jobs of a worker
  that died mid-run.
- SPA: the report page handles `202` by showing the job state with **Cancel**
  and polling (0.5 s backing off to 3 s, stopped when the spec changes); the
  finished result shows "Background job" and exports from the job. The results
  line shows "Cached result from …" or the run time. **Audit log** page
  (sidebar, permission-gated): filters, user links, expandable rows with the
  spec ("Open this report"), scope, error, database and job. The delete dialog
  explains out-of-scope cascades. All strings are in the en/fa dictionaries.
- Demo: groups "Sales: Tehran region" (Tehran, Karaj, Qom) and "Sales: East
  region" (Mashhad, Kerman) are limited through `rule(City, …)`,
  `rule(OrderItem, …)` and `row_rules` on the Order/Customer options (by
  `City.name_en`, so it works for both seed locales); "Shop managers" see
  everything plus *Refunds* and the audit log. `seed_demo` always (re)creates
  the groups and their permissions; `--users [--password]` creates `admin`,
  `manager`, `tehran` and `east`.

Not yet at contrib.admin parity (deliberately deferred): inlines, file
uploads, `date_hierarchy`, list editing, custom form widgets/fieldsets, object
tools, permission/user "change password" special forms.
