## 1. Vision

A from-scratch, installable Django app that replaces `django.contrib.admin` and
adds **deep, BI-grade reporting** plus a **natural-language report interface**:
a non-technical user types a request in plain language (Persian first, English
second) such as *"revenue for the last three months by city"* and gets a table,
chart, or dashboard — without knowing any table or field names.

### Positioning (why this exists)

Mature BI tools already exist (Metabase, Apache Superset, Redash). They connect
to the raw database and see only tables and columns. This project's edge is
that it **understands Django**:

- models, relations, choices, verbose names, managers, and custom querysets;
- Django's permission system, plus row-level rules defined in code;
- business logic expressed once in Python (a semantic layer), reused by the UI,
  the query engine, and the natural-language interface.

Secondary differentiators, weak in existing tools:

- **First-class Jalali (Solar Hijri) calendar**: grouping, filtering, and
  relative periods computed in the database, not just at display time.
- **Proper RTL UI** with Persian digits and locale-aware number formatting.

### Non-goals (for v1)

- Not a general BI tool for non-Django databases.
- Not a CMS / page builder.
- No arbitrary SQL generated by an LLM (see §6).
- No multi-database federation in v1.

## 2. Background decisions (already made)

1. **Stay on Python/Django.** Rewriting Django itself in Rust is not justified;
   the value of Django is development speed and its dynamic introspection.
   Rust may later be used only for measured hot paths (via PyO3/maturin), and
   Granian (Rust ASGI server) is an acceptable deployment option.
2. **Build on the ORM, not raw SQL.** The query engine compiles a structured
   report spec into Django ORM querysets, so permissions, managers, and
   row-level rules apply automatically and SQL injection is structurally ruled
   out.
3. **The LLM never writes SQL.** It produces a structured `ReportSpec` (JSON)
   constrained to the semantic layer's catalog; the spec is validated and then
   executed by the same engine the GUI uses.
4. **Semantic layer is the core asset.** Quality of the NL interface depends far
   more on good labels/synonyms/descriptions than on the model used.

## 3. Architecture overview

```
┌──────────────────────────────────────────────────────────────────┐
│ Frontend (SPA: React or Vue)  — RTL, Jalali, ECharts, data grid  │
└───────────────▲──────────────────────────────────────────────────┘
                │ JSON API (DRF or django-ninja)
┌───────────────┴──────────────────────────────────────────────────┐
│ 1. Model discovery   — introspect apps/models/fields/relations   │
│ 2. Semantic layer    — dimensions, measures, labels, synonyms    │
│ 3. Query engine      — ReportSpec → validated → Django ORM       │
│ 4. Execution layer   — async jobs, replica routing, cache        │
│ 5. Access control    — Django perms + row-level rules            │
│ 6. NL interface      — text → ReportSpec via LLM structured out  │
└───────────────┬──────────────────────────────────────────────────┘
                │
        Primary DB (writes) / Read replica (reports) / optional DuckDB|ClickHouse
```

### 3.1 Model discovery

- Walk `django.apps.apps.get_models()`; for each model read `_meta`:
  fields, internal types, `choices`, `verbose_name`, nullability, FK/M2M/reverse
  relations, `related_model`.
- Build a **relation graph** so users can traverse `Order → Customer → City`.
- Output: an in-memory registry (cached; rebuilt on startup / app reload).
- Drives the auto-generated CRUD (the "replace contrib.admin" part).

### 3.2 Semantic layer

Declared in Python by developers, registered per model. Concepts:

- **Dimension**: a groupable/filterable attribute (field or lookup path, or an
  expression). Has type (`time`, `category`, `number`, `boolean`, `geo`).
- **Measure**: a named aggregation with business logic baked in.
- **Labels / synonyms / descriptions**: in Persian and English; these are the
  primary context for the NL interface.
- **Default time dimension** per semantic model.

Sketch:

```python
from django.db.models import Sum, Count, Avg, Q
from bi_admin.semantic import Semantic, Dimension, Measure, register


@register
class OrderMetrics(Semantic):
    model = Order
    time_dimension = "created_at"

    dimensions = {
        "created_at": Dimension(
            "created_at", type="time", label={"fa": "تاریخ ثبت سفارش", "en": "Order date"}
        ),
        "paid_at": Dimension(
            "paid_at", type="time", label={"fa": "تاریخ پرداخت", "en": "Payment date"}
        ),
        "city": Dimension(
            "customer__city__name",
            type="category",
            label={"fa": "شهر", "en": "City"},
            synonyms={"fa": ["استان", "محل"]},
        ),
        "status": Dimension("status", type="category"),
    }

    measures = {
        "revenue": Measure(
            Sum("amount", filter=Q(status="paid")),
            label={"fa": "درآمد", "en": "Revenue"},
            synonyms={"fa": ["فروش", "گردش مالی", "دریافتی"], "en": ["sales"]},
            description={
                "fa": "جمع مبلغ سفارش‌های پرداخت‌شده",
                "en": "Sum of amounts of paid orders",
            },
            format="currency",
        ),
        "orders": Measure(Count("id"), label={"fa": "تعداد سفارش", "en": "Orders"}),
        "aov": Measure(Avg("amount"), label={"fa": "میانگین سبد", "en": "Avg order value"}),
    }
```

### 3.3 Query engine

Input: a `ReportSpec`. Output: rows + column metadata.

Responsibilities:

- Validate every measure/dimension/filter against the semantic catalog.
- Compile to ORM: `.filter()`, `.annotate()`, `.values()`, aggregation,
  `Trunc*` for time grains, `Window` functions (running totals, rank, share of
  total, period-over-period), subqueries.
- Apply access control (see 3.5) **inside the engine**, never in the UI.
- Enforce limits: max rows, max dimensions, statement timeout.
- Drill-down: given a cell (dimension values), return the underlying records
  queryset.

`ReportSpec` (pydantic, also the LLM output schema):

```python
from typing import Literal
from pydantic import BaseModel


class Filter(BaseModel):
    field: str  # dimension key
    op: Literal["eq", "neq", "in", "not_in", "gte", "lte", "between", "contains", "is_null"]
    value: str | int | float | bool | list | None = None


class Sort(BaseModel):
    field: str  # measure or dimension key
    direction: Literal["asc", "desc"] = "desc"


class ReportSpec(BaseModel):
    semantic_model: str
    measures: list[str]
    dimensions: list[str] = []
    filters: list[Filter] = []
    time_dimension: str | None = None  # defaults to model's
    time_grain: Literal["day", "week", "month", "season", "year"] | None = None
    calendar: Literal["jalali", "gregorian"] = "jalali"
    relative_period: str | None = None  # e.g. "last_3_months", "last_year",
    # "this_season" — resolved in code
    compare_to: Literal["previous_period", "same_period_last_year"] | None = None
    sort: list[Sort] = []
    limit: int | None = 1000
    chart: Literal["table", "bar", "line", "area", "pie", "pivot", "kpi"] = "table"
    clarification_needed: str | None = None  # set by the LLM when ambiguous
```

Optional raw-SQL mode for power users only: read-only DB role, separate
connection alias, `SET statement_timeout`, row limit, audited.

### 3.4 Execution layer

- Heavy reports run as background jobs (Celery, or the Django tasks framework
  if available in the chosen Django version); the UI polls or receives push
  updates.
- Database router sends report queries to a read replica when configured.
- Result cache keyed by (normalized spec, user's row-level scope, data version).
- Pre-aggregation: materialized views / summary tables for hot reports.
  *(M7: declarative summary tables answered from only when provably exact.)*
- Later: optional columnar engine (DuckDB to start, ClickHouse at scale) fed by
  periodic sync; the engine picks the backend per semantic model. *(M7: DuckDB
  ships as an optional extra; ClickHouse has an interface, no implementation.)*

### 3.5 Access control

- Model-level: reuse Django permissions (`view_*`).
- Semantic-level: per measure/dimension visibility (e.g. hide `margin`).
- Row-level: pluggable rules, e.g.
  `rule(OrderMetrics, lambda user: Q(branch=user.profile.branch))`.
- Applied in the query engine for GUI, API, NL, and drill-down alike.
- Audit log of every report execution (user, spec, duration, row count).

### 3.6 Frontend

- SPA (React + TypeScript, Vite) served by Django.
- Components: auto CRUD lists/forms, report builder (pick measures/dimensions/
  filters), pivot table, charts (ECharts), dashboards (grid of widgets with
  global filters), drill-down, export (XLSX/CSV), scheduled email reports.
- RTL-first layout, `dir="auto"` on user-generated text, Persian digits, Jalali
  date pickers.
- Data grid candidates: AG Grid (community) or TanStack Table.

## 4. Jalali calendar requirements

- Grouping by Jalali month/season/year **must happen in the database**: Jalali
  months do not align with Gregorian months, so converting after aggregation is
  wrong.
- Approach options (evaluate in milestone 2):
  1. A calendar dimension table (one row per day: gregorian date, jalali
     y/m/d, season, week, holiday flags) joined on date — portable and fast.
  2. DB functions (PostgreSQL SQL/PLpgSQL function for jalali conversion)
     exposed as Django `Func` expressions.
- Prefer option 1 (also enables holidays/working days in reports).
  **Decided in M2: option 1** (`bi_admin.CalendarDay`, see §10).
- Relative periods ("last year", "this season", "last 3 months") resolve in
  deterministic Python code against today's Jalali date — never by the LLM.
- Library for Python-side conversion: `jdatetime` (verify current status).

## 5. Natural-language interface

Reference for the implemented interface (pipeline, privacy, providers,
configuration, connecting a model, evaluation, next steps):
[docs/nl-interface.md](docs/nl-interface.md). This section is the original
design; the decisions taken are in §10 (M5, M6).

### 5.1 Pipeline

```
user text (fa/en)
  → retrieve relevant catalog entries (embeddings over labels/synonyms/descriptions)
  → LLM call with structured output (ReportSpec JSON schema)
  → validate against semantic layer
      ↳ invalid: send errors back to LLM, retry (max 2)
      ↳ clarification_needed: ask the user, stop
  → resolve relative dates + match category values (fuzzy/value index)
  → render human-readable interpretation ("Paid revenue by city, 1 Tir → today")
  → execute via query engine (same perms) → table/chart
```

### 5.2 Prompt context

- Semantic catalog subset (keys, labels, synonyms, descriptions, types).
- Today's date in both calendars.
- Few-shot examples (curated + learned from user corrections).
- Previous `ReportSpec` when the user is refining ("now only Tehran",
  "make it monthly") — the model edits the spec rather than starting over.

### 5.3 Hard problems to handle

- **Value matching**: user writes "تهران", DB has "Tehran" or a variant. Keep
  a distinct-values index per category dimension; fuzzy + transliteration +
  optional embedding match.
- **Ambiguity**: multiple time dimensions, overlapping measure names → ask.
- **Large schemas**: never dump the whole catalog; retrieve top-k.
- **Explainability**: always show the interpretation sentence and let the user
  adjust via normal filter UI.

### 5.4 Provider abstraction & privacy

- Only the catalog and the user's text go to the LLM — never row data.
- Use an OpenAI-compatible client interface so hosted models and local
  servers (Ollama, vLLM) are interchangeable via settings.
- Cache NL → spec results; log prompts/outputs for evaluation (opt-in).

### 5.5 Evaluation

- Golden set: ≥100 real Persian (and some English) questions with expected
  `ReportSpec`s, stored as fixtures; run in CI against a stub or real model.
- Metrics: exact/semantic spec match rate, clarification rate, retry rate.
- Every user correction becomes a candidate golden example + few-shot.

## 6. Security principles

1. No LLM-generated SQL, ever. LLM output is data (a spec), validated.
2. Access control lives in the query engine.
3. Raw SQL mode: opt-in, read-only role, timeout, row limit, audited.
4. Resource limits on every query (timeout, row cap, dimension cap).
5. Exports respect the same row-level scope.
6. Secrets (LLM keys, DB credentials) only via settings/env.

## 10. Decisions & open questions

Decided (M0, 2026-10-18):

- Frontend: **React + TypeScript** (Vite).
- API: **django-ninja** — `ReportSpec` doubles as API schema and LLM output schema.
- Minimum versions: **Django 5.2 LTS, Python 3.12, PostgreSQL 16**.
- Tests run on SQLite by default; CI also runs PostgreSQL 16
  (`GOZAR_DB=postgres`). Jalali/DB-function work in M2 targets PostgreSQL.
- Distribution name `gozar`, import package `bi_admin`.

Decided (M1, 2026-10-18):

- License: **MIT**.
- Discovery (`bi_admin.discovery`): lazily built, process-wide `Registry` of
  `ModelInfo`/`FieldInfo`/`RelationInfo` read from `_meta`; relations are
  stored in both directions with a `many` flag; `find_path` (BFS, to-one hops
  first) and `resolve_lookup` (validates `a__b__c` paths) are the building
  blocks M2's validator will reuse. Hidden by default: contenttypes, sessions,
  admin, bi_admin, `auth.permission`; tune with `GOZAR["INCLUDE_APPS"|
  "EXCLUDE_APPS"|"EXCLUDE_MODELS"]`.
- CRUD (`bi_admin.crud`): `ModelOptions` mirrors the core of `ModelAdmin`
  (`list_display` incl. lookup paths and callables, `search_fields` with
  `^ = @`, `list_filter`, `ordering`, `fields`/`exclude`/`readonly_fields`,
  `list_per_page`, actions, permission and save/delete hooks), registered via
  `@register(Model)` in an app's auto-discovered `gozar.py`. Defaults are
  derived from `_meta`. Validation goes through a generated `ModelForm`.
- Permissions: staff session + CSRF on every endpoint; Django `view/add/
  change/delete` perms (change implies view); deletion also requires delete
  permission on every cascaded registered model, and PROTECT/RESTRICT returns a
  409 with the blocking objects. Filters/ordering accept only declared paths, so
  a filter can't be used as an oracle on hidden fields (e.g. password hashes).
  Password fields are write-only and hashed with `set_password`.
- History: `bi_admin.ChangeLog` (add/change/delete with changed field names),
  the counterpart of admin's `LogEntry`. *(M4 kept the report audit log in its
  own model, `ReportLog`.)*
- Search normalises Arabic ي/ك to Persian ی/ک (and back) per term.
- UI: React SPA built by Vite into `bi_admin/static/bi_admin/spa/` (git-ignored,
  shipped as a wheel artifact); Django serves the shell (`bi_admin.views.spa`)
  via the Vite manifest. Dates are shown in Jalali via `Intl`
  (`fa-IR-u-ca-persian`), numbers with Persian digits. Date inputs are still
  Gregorian browser pickers — Jalali pickers come with M3. *(Superseded by the
  i18n decisions below: English/Gregorian are now the defaults.)*

Decided (M2, 2026-10-18):

- Semantic API (`bi_admin.semantic`): subclass `Semantic` (`model`, optional
  `name`, `label`, `synonyms`, `description`, `time_dimension`, `dimensions`,
  `measures`) and decorate with `@register` in an app's `gozar.py`. The key in
  `ReportSpec.semantic_model` defaults to the snake-cased class name
  (`OrderMetrics` → `order_metrics`). Models bind lazily: dimension paths are
  checked with `Registry.resolve_lookup`, measure expressions are resolved
  against the model without querying; mistakes raise `ImproperlyConfigured` and
  surface as system check `bi_admin.E001`. Labels/descriptions normalise to
  `{"fa", "en"}` (a bare string is Persian; defaults come from verbose names),
  synonyms to per-language lists. Dimension `type` is inferred from the field
  (date/datetime → time, numbers → number, boolean, otherwise category);
  expression dimensions need an explicit type. `hidden=True` keeps an item out
  of the catalog and the validator. `catalog(lang, request)` lists what a user
  may report on.
- Permissions: `Semantic.has_permission` defaults to the CRUD view permission
  of the model (change implies view) and `get_queryset` to the CRUD options'
  queryset, so reports and CRUD see the same rows. M4 adds row-level rules on
  top of `get_queryset` (see the M4 decisions).
- `ReportSpec` (`bi_admin.engine.spec`) is the §3.3 model with
  `extra="forbid"`. Filter values for time dimensions are dates, Gregorian
  (`2026-03-21`) or Jalali (`1405/01/01`, any year below 1700), Persian digits
  allowed; a category value may be its choice label (`پرداخت‌شده` → `paid`).
- Validator (`bi_admin.engine.validate`) collects every problem into
  `SpecError(code, message, path, value, suggestions)`; suggestions match keys,
  labels and synonyms (Arabic ي/ك normalised) and then fuzzy matches. Codes:
  `unknown_semantic_model`, `unknown_measure`, `not_a_measure`,
  `unknown_dimension`, `not_a_dimension`, `invalid_lookup`, `duplicate`,
  `no_measures`, `too_many_dimensions`, `no_time_dimension`,
  `not_a_time_dimension`, `unknown_relative_period`, `invalid_operator`,
  `invalid_value`, `invalid_choice`, `measure_filter_not_supported`,
  `sort_field_not_in_report`, `unknown_field`, `invalid_limit`,
  `limit_exceeded`, `not_supported` (`compare_to`, until M6; M6 replaced it with
  `compare_needs_period`) and `clarification_needed`. Caps: `GOZAR["REPORT_MAX_ROWS"]` (10 000; also the
  limit when `limit` is null) and `GOZAR["REPORT_MAX_DIMENSIONS"]` (6).
  Filtering on measures (HAVING) is deferred.
- Time semantics: `time_grain` adds the time dimension (spec's or the model's
  default) as the first group key; any time dimension listed in `dimensions` is
  bucketed too (grain defaults to `day`). Null times form a null bucket, sorted
  last. All date logic uses local dates in `TIME_ZONE`; date filters and
  periods compile to half-open aware datetime ranges so indexes still apply.
  Default order: chronological when bucketed, else first measure descending;
  remaining group keys always break ties so `LIMIT` is deterministic.
- Jalali grouping: calendar dimension table `bi_admin.CalendarDay` (one row per
  day: Gregorian y/q/m/d, ISO week, Jalali y/season/m/d, Saturday-based Jalali
  weekday, `*_start` dates of the enclosing week/month/season/year in both
  calendars, `is_weekend` (Friday; `GOZAR["WEEKEND_DAYS"]`), `is_holiday` +
  `holiday_name` for the fixed solar holidays — lunar holidays move every year
  and must be added per row). The compiler groups by a correlated lookup
  `(SELECT jalali_month_start FROM bi_admin_calendarday WHERE date =
  local_date(created_at))`; Django groups by select position on SQLite and
  PostgreSQL, verified on both. Gregorian grains use `Trunc*` (ISO weeks start
  Monday; `season` = calendar quarter) and need no table. A Jalali query whose
  dates the table doesn't cover fails with `409 calendar_not_populated` rather
  than returning null buckets. `manage.py gozar_calendar [--start] [--end]
  [--clear]` fills it (default: 15 Jalali years back to the end of the year 5
  ahead; idempotent; keeps edited rows). The per-row lookup is a PK probe; if it
  shows up in profiles, M4/M7 can denormalise a date key or pre-aggregate.
- Result shape: a bucket's value is its Gregorian start date (ISO) plus a
  neutral label in `<key>__label` (`1405-07`, `1405-S3`, `1405`, `2026-W42`,
  `2026-Q4`); the UI formats month/season names. Decimals become ints when
  integral (within 2^53), otherwise floats. The response carries `columns`
  (role, type, fa/en label, grain, calendar, choices, format), `rows`,
  `truncated`, the normalised `spec` and the resolved `period`.
- Relative periods (`bi_admin.calendar.periods`): `today`, `yesterday`,
  `this_<unit>` (to date), `last_<unit>`, `last_<N>_<unit>s` (N complete units
  before the current one) and `past_<N>_<unit>s` (current unit to date plus the
  N-1 before it); units day/week/month/season(=quarter)/year; in the spec's
  calendar; resolved against `periods.today()` (= `timezone.localdate()`, which
  tests monkeypatch).
- API: `GET /api/reports/catalog?lang=fa|en`, `POST /api/reports/validate`,
  `POST /api/reports/run` — staff session + CSRF like CRUD; `403
  permission_denied` without the model's view permission, `422` with structured
  errors for an invalid spec (pydantic's own 422 for schema errors). Suggestions
  for an unknown semantic model only list models the user may see.
- Demo `OrderMetrics` (`example_project/shop/gozar.py`) follows §3.2, plus
  `province`, `customer` and `amount` dimensions and `paid_orders`/`customers`
  measures. Two deliberate changes from the sketch: `aov` averages paid orders
  only (consistent with `revenue`), and the synonym "استان" moved from `city` to
  the new `province` dimension.

Decided (i18n + preferences, 2026-10-18):

- **English is the source language and the default; Gregorian is the default
  calendar.** Persian and Jalali stay fully supported as per-user choices.
  This revises the Persian-first framing of §1 for the UI: the product is
  bilingual, and Persian is still first-class (RTL, digits, Jalali in the DB).
- Backend strings use gettext: error messages, the CRUD "Delete selected"
  action, `ChangeLog` fields and action choices, `CalendarDay` and
  `UserPreferences` verbose names, the SPA shell template. The Persian catalog
  lives in `src/bi_admin/locale/fa/LC_MESSAGES/` with the compiled `.mo`
  committed (CI needs no gettext tools); regenerate with `django-admin
  makemessages -l fa` + `compilemessages` from `src/bi_admin`. The demo shop
  does the same in `example_project/shop/locale/`. Verbose names follow the
  Django convention (lower-case English, e.g. `order`); `path_label` and

Decided (M3 — report UI, 2026-10-19):

- Reports area at `/reports` (sidebar), lazy-loaded so ECharts (~580 kB) only
  loads there. Builder on the side, results beside it; on narrow screens they
  stack. Everything is driven by `GET /reports/catalog` (in the user's
  language).
- **The URL is the state**: the builder edits a `ReportSpec` serialised as
  `?spec=<json>` (empty/default keys dropped), so reports are shareable and
  reloadable; "Copy link" copies it. Saved reports in the database are left
  for M6 (dashboards), where they are needed anyway. *(Done in M6: `?saved=<id>`
  next to `?spec=`.)*
- Live editing: every change is validated (`POST /reports/validate`, 350 ms
  debounce) and, when valid, run. Half-filled filters are left out of the
  request (and error paths are mapped back to the original filter rows), so
  adding a filter doesn't flash errors. Errors render next to their section by
  `path` (`measures[0]`, `filters[2].value`, `limit`, …), with suggestions
  shown by label. Changing only the chart type never re-queries.
- Time controls: date field, grain, calendar ("my calendar" = the user's
  preference, or force Gregorian/Jalali), and a period that is either a
  relative period preset or a custom range. The custom range is stored as a
  `between` filter on the time dimension (no new spec field) and shown in the
  time section instead of the filter list.
- Filter value pickers: `GET /reports/values` returns a dimension's values —
  its choices (labels in the user's language), related objects searched with
  the target's `search_fields` (the CRUD autocomplete rules, Arabic/Persian
  letters included) when the path ends on a relation, otherwise distinct
  values from the semantic queryset (`icontains`, limit 50). Time dimensions
  use the date picker; numbers a text input (Persian digits accepted).
- Results: a client-side sortable table (dimension values formatted —
  time buckets as "Oct 2026" / "مهر ۱۴۰۵", "Q4 2026" / "پاییز ۱۴۰۵", choices by
  label; measures by their `format`: currency/integer without decimals,
  percent as %, decimal with 2), bar/line/area/pie (ECharts), pivot (exactly
  two group-by fields; rows × columns of one measure) and KPI cards (no
  group-by). Charts plot one measure at a time (a selector appears when there
  are several, so scales don't clash); a second group-by field becomes the
  series. ECharts gets the user's digits and compact number format on axes,
  bucket labels in the report's calendar, the page font, and in RTL a
  reversed category axis, the value axis on the right and right-aligned
  legends. Unsuitable chart/shape combinations show a hint instead of a broken
  chart. The pivot has no totals column: totals of non-additive measures
  (averages, distinct counts) can't be derived client-side; M6 may add server
  totals. *(M6 didn't: see the M6 decisions.)*
- Drill-down (`POST /reports/drilldown` → `bi_admin.engine.drilldown`): the
  clicked group values become extra filters on the spec — a time bucket becomes
  a `between` covering the bucket (it must start a bucket of that grain in the
  report's calendar), `null` becomes `is_null` — and the narrowed spec goes
  through the normal validator and compiler, so lookups, coercion, choice
  labels, the semantic `get_queryset` and permissions are identical to the
  report. Clicking a measure also applies that aggregate's own `filter=Q(...)`
  (revenue → paid orders), so record counts match the cell for count-like
  measures (tests assert this for every cell of a report). Errors point at
  `cell.<key>` / `measure`. Rows are serialised like the CRUD list (its
  `list_display`, ordering, `select_related`), paginated (25, max 200), and
  link to the CRUD detail pages; `.distinct()` when a filter crosses a
  to-many relation.
- Export (`POST /reports/export?format=csv|xlsx`): runs the spec through the
  same `run()` (permissions, limits) and writes the result with headers in the
  user's language, bucket labels for time columns and choice labels for
  choices. CSV is UTF-8 with a BOM (spreadsheet apps detect Persian text);
  XLSX (openpyxl, new dependency) has a bold frozen header, number formats per
  measure format and a right-to-left sheet for Persian users. The SPA
  downloads via `fetch` + blob (POST with CSRF).
- Date picker (`components/DatePicker.tsx`): a dependency-free month grid in
  the user's calendar (Jalali weeks start Saturday, Gregorian Monday), values
  always Gregorian ISO dates. Gregorian→Jalali uses `Intl`'s Persian calendar;
  Jalali→Gregorian starts from an estimate and corrects with `Intl`
  (round-trip verified for every day 1990–2040). Used in the report builder,
  the CRUD list date filters and the CRUD form (date fields, and date + time
  for datetime fields), replacing the native Gregorian inputs.

Decided (M4 — access control & execution, 2026-10-19):

- Settings: every `GOZAR` key and its default lives in `bi_admin/conf.py`
  (`setting(name)`); the validator's caps moved there too.
- **Row-level rules** (`bi_admin.access.rules`): a rule is a callable taking the
  *user* (not the request, so background jobs evaluate it identically) and
  returning a `Q`, `True`/`None` (no restriction) or `False` (no rows). Declared
  with `rule(target, fn)` / `@rule(target)` — target a model, an `"app.model"`
  label or a `Semantic` — or as `row_rules = [...]` on `ModelOptions` /
  `Semantic`. All applicable rules are AND-ed: model rules apply to that model's
  CRUD, to every relation picker listing it and to every semantic model over it;
  semantic rules add to those for reports only. They are applied *outside* the
  overridable hooks: `model_queryset(options, request)` =
  `options.get_queryset` + rules, `semantic_queryset(sem, request)` =
  `Semantic.get_queryset` + model rules + semantic rules, so a custom
  `get_queryset` can't drop them. Evaluated once per request (memoised on it).
  Fail closed: a rule that raises or returns something else denies every row
  (logged). Superusers bypass rules unless `ROW_RULES_BYPASS_SUPERUSER = False`.
  `request=None` (trusted code, e.g. `run(spec)` in a shell) is unrestricted.
- Every path is scoped: report run, drill-down, export, value lookups (distinct
  values from the scoped semantic queryset; relation values from the target
  model's scoped queryset), jobs; CRUD list (and its unfiltered total), filter
  choices, detail, update, delete, history, autocomplete, actions (the selection
  is intersected with the scope) and delete plans. Writes: relation form fields
  only accept rows in scope — plus the ones already linked, so editing other
  fields never fails on a hidden link — and a save whose row would end up outside
  the scope is rolled back with `403 out_of_scope`. A delete whose cascade would
  reach rows outside the user's scope is refused (`out_of_scope` in the plan,
  `409` on delete); protected-object samples never name hidden rows. `validate`
  touches no rows, so only visibility applies there. *(The M2M gap noted here
  was closed in the bug-fix round below.)*
- **Semantic visibility**: `Dimension`/`Measure` take `permission=` — a
  permission name, a list (all required) or a predicate on the user (a failing
  predicate hides the item). `Semantic.is_visible(item, request)` is the hook;
  `visible_dimensions/measures(request)` and `default_time_dimension(request)`
  build on it, and the catalog, validator (hence run, drill-down, export, jobs)
  and value lookups use them, so a hidden key gets exactly the error and
  suggestions an unknown one would (`unknown_measure`, `unknown_dimension`,
  `unknown_field` in sort — never `sort_field_not_in_report`); suggestions and
  synonym matches never reveal it. A hidden default time dimension behaves as
  none. Superusers pass permission strings (they have every permission), but
  predicates decide for everyone. Drill-down drops list columns whose path (or
  a relation leading to it) is read only by items the user can't see — paths of
  invisible items minus paths of visible ones (`Semantic.hidden_fields`), using
  the dimension paths and the measures' aggregated fields (not their `filter=`).
  `hidden=True` still means "internal", not a permission. Demo: *Refunds*
  needs `shop.change_order`.
- **Audit log**: new model `bi_admin.ReportLog` (user + username copy, kind
  run/export/drilldown, semantic model, normalised spec — the resolved calendar
  included — scope, status ok/invalid/denied/failed, error code and message,
  duration, row count, cache hit, database, job). Written by
  `access.audit.record()` around every execution in the engine, so API, jobs
  and code with a request are covered, including refused (403 → `denied`),
  invalid (422 → `invalid`, first error code) and failed ones (timeouts,
  `calendar_not_populated`, `internal_error`). `validate` and value lookups
  aren't executions and aren't logged; exporting a finished job's stored result
  is. The scope column is the WHERE clause of the user's scoped base queryset
  (`""` = all rows), which also captures custom `get_queryset` filters. The
  insert runs in its own savepoint and never masks the report's own outcome;
  `AUDIT_REPORTS = False` turns it off. Readable with the model's view
  permission `bi_admin.view_reportlog` (the model has no add/change/delete
  perms) through `GET /api/audit/reports` (filters user, status, kind,
  semantic_model, error_code, `q`; paginated) and the SPA's **Audit log** page;
  `/auth/me` returns `permissions.audit`. `ChangeLog` was not extended: it
  records object edits keyed by model/pk, a different shape and audience.
- **Limits**: `REPORT_MAX_ROWS` (10 000), `REPORT_MAX_DIMENSIONS` (6, the time
  grain counts) and the new `REPORT_MAX_FILTERS` (20 → `too_many_filters`) are
  validator errors (422). `REPORT_STATEMENT_TIMEOUT_MS` (30 000; 0 = off) wraps
  every report, drill-down and value query (`execution.limits`): PostgreSQL runs
  them in a transaction with `set_config('statement_timeout', ms, true)` (=
  `SET LOCAL`), restoring the previous value afterwards because a savepoint
  inside an outer transaction would otherwise keep it, and maps SQLSTATE 57014;
  SQLite installs a progress handler (every 1000 VM steps) that interrupts the
  statement past the deadline; other backends run unlimited. Both map to `504
  statement_timeout` with `timeout_ms`.
- **Result cache** (`execution.cache`, Django's cache framework, alias
  `REPORT_CACHE`, `REPORT_CACHE_TIMEOUT` = 300 s, 0 = off; on by default). Key =
  SHA-256 of the normalised spec without `chart` (chart switches share an
  entry), the resolved period, an exact scope fingerprint (the scoped base
  queryset's SQL with typed params — `str(query)` inlines params unquoted, so it
  is only used for display), the language (column labels), the reports database
  and the data versions. Dependencies are read off the compiled SQL: every
  model whose quoted table name appears (joins, subqueries such as the
  calendar lookup or a rule's `__in` subquery) plus the semantic model's own.
  A data version is a random token per model (plus a global epoch for
  `bump_all()`), replaced on `post_save`/`post_delete`/`m2m_changed` — at once
  (the writer's own transaction) and again `on_commit` (a reader that cached
  pre-commit data in between is invalidated). A missing (evicted) version gets
  a new random token, so it can't resurrect old entries. Receivers are
  connected per model, skipping Gozar's bookkeeping and Django's plumbing, so
  those keep Django's fast bulk delete. Bulk writes send no signals:
  `cache.bump(Model)` is called by CRUD actions, `gozar_calendar` and
  `seed_demo`. Permission and validation always run before the lookup; errors
  are never cached. The run response has `cache: {enabled, hit, stored_at}`;
  `?cache=false` on run/export/jobs bypasses the lookup but stores the fresh
  result; the SPA's **Refresh** does that. The cache must be shared across
  processes for the worker's results to be reused — the demo uses
  `FileBasedCache` in `example_project/.cache` (tests: `LocMemCache`).
- **Read-replica routing** (`execution.router`): `reporting(alias)` sets a
  context variable while report, drill-down, export and value-lookup queries
  run; `ReportsRouter.db_for_read` returns it, and the engine also passes the
  alias explicitly (`QuerySet.using`), so the main queries are routed even
  without the router. CRUD reads, all writes, permission/preference reads, the
  audit log and jobs stay on `default`. Checks: `bi_admin.E002` (alias not in
  `DATABASES`), `bi_admin.W001` (router not installed). The demo defines a
  `replica` alias (same SQLite file in development, a separate test database —
  `test_gozar_replica` on PostgreSQL — in tests); `GOZAR_REPORTS_DATABASE=replica`
  enables it. Cache entries are per database.
- **Background jobs** (`execution.jobs`): model `bi_admin.ReportJob` (UUID pk,
  owner, spec, options = submitter's language/calendar/cache flag, status
  queued/running/done/failed/cancelled, timestamps, result JSON = the `/run`
  body, error payload + HTTP status). Synchronous by default; async when
  `?mode=async`, or `mode=auto` (default) and `Semantic.run_async` /
  `REPORT_ASYNC` say so; `mode=sync` forces it. Submitting validates first
  (403/422 come back at once, no job) and returns a cached result directly
  (`200`); otherwise `202 {"job"}`. Endpoints `POST /reports/jobs`, `GET
  /reports/jobs`, `GET /reports/jobs/{id}`, `/result` (the run body; `409
  job_not_finished`, `410 job_cancelled`, or the failure with the status a
  synchronous run would have had), `POST /{id}/cancel`, `GET /{id}/export`
  (from the stored result, no new query). Jobs are private: another user's job
  is a `404 job_not_found`. Pluggable `JOB_BACKEND` with `submit(job)`:
  `DatabaseBackend` (default; nothing to do, `manage.py gozar_worker [--burst]
  [--sleep] [--max-jobs] [--keep-days 7]` claims jobs) and `ImmediateBackend`
  (runs inside the request; tests and development). A worker claims with a
  conditional `UPDATE … WHERE status='queued'` (portable, no `SKIP LOCKED`
  needed) and runs the job as the owner with a request stand-in
  (`JobRequest`) in their language, so permissions, visibility and rules are
  re-checked at execution time (a user who lost access gets a failed job with
  403). A job cancelled while running stays cancelled. Finished jobs older
  than `--keep-days` are purged. *(Leases for jobs of a dead worker: see the
  bug-fix round below.)*
- SPA: the report page handles `202` by showing the job state with **Cancel**
  and polling (0.5 s backing off to 3 s, stopped when the spec changes); the
  finished result shows "Background job" and exports from the job. The results
  line shows "Cached result from …" or the run time. **Audit log** page
  (sidebar, permission-gated): filters, user links, expandable rows with the
  spec ("Open this report"), scope, error, database and job. The delete dialog
  explains out-of-scope cascades. All strings are in the en/fa dictionaries.
- Demo: groups "Sales: Tehran region" (Tehran, Karaj, Qom) and "Sales: East
  region" (Mashhad, Kerman) are limited through `rule(City, …)`,
  `rule(OrderItem, …)` and `row_rules` on the Order/Customer options (by
  `City.name_en`, so it works for both seed locales); "Shop managers" see
  everything plus *Refunds* and the audit log. `seed_demo` always (re)creates
  the groups and their permissions; `--users [--password]` creates `admin`,
  `manager`, `tehran` and `east`.

- **API docs** (`bi_admin.api.docs`): django-ninja reverses

  shell's `basePath`/`apiBase` use the resolved namespace the same way. Access:
  `GOZAR["API_DOCS"] = "staff"` (default; like the rest of the API — anonymous

  login page follows for same-origin paths; `openapi.json` answers 401, non-staff

  (`bi_admin/api_docs.html`: ninja's CDN page with Gozar's favicon — ninja's
  favicon is hot-linked from its website and blocked by browsers) and always
  sends the CSRF token, so "Try it out" works with the session.
- **Related rows in serialized objects**: detail payloads (and create/update
  responses) list only M2M links the user may see — the target model's
  `get_queryset` + row rules — and report the rest as `hidden_links: {field:
  count}` (the form says "+N linked records you can't see (kept when you
  save)"); the count is the one thing revealed, as with delete plans. Saving
  keeps hidden links: a submitted M2M list replaces the visible ones and the
  hidden ones are added back, so the SPA (which sends every field) never drops
  them; a hidden row that isn't linked yet still can't be added. A forward FK
  to a hidden row is a `restricted` ref (`{"pk", "model", "label":
  "Restricted", "restricted": true}`) that round-trips unchanged on save. List
  and drill-down cells read through a hidden related row (`customer`,
  `customer__city__name`, …) are restricted too, checked per to-one hop with one
  query per (column, ruled model) per page (`service.serialize_rows`). Reverse
  relations can now be listed in `ModelOptions.fields` (e.g. `"orders"` on
  Customer): read-only, scoped the same way, at most 100 shown, described in the
  model metadata as a read-only `m2m` field.
- **Job leases**: `ReportJob` gained `lease` (a random token per claim),
  `heartbeat_at` and `attempts`. `claim()` stamps all three; while a job runs, a
  daemon thread (`jobs.Heartbeat`, every third of `JOB_LEASE_SECONDS` = 60)
  refreshes the heartbeat and stops once the lease is no longer its own.
  `jobs.recover_stale()` — run by `gozar_worker` at start and then once per
  lease period — requeues running jobs whose heartbeat is older than the lease,
  until `JOB_MAX_ATTEMPTS` (3), then marks them failed with `500 worker_lost`
  (and `attempts`). Every update (heartbeat, outcome, recovery) is conditional
  on the lease token, so a worker presumed dead that comes back can't overwrite
  a later attempt. `ImmediateBackend` runs without a heartbeat (it's inside the
  request); `execute(job_id)` — what a custom Celery/RQ backend calls — keeps it.
  The job payload includes `attempts`.
- **Favicon**: `bi_admin/static/bi_admin/favicon.svg`, linked from the SPA shell
  and the docs page. A browser smoke test (all pages, every CRUD list and a
  detail page, the reports page with a drill-down, the docs, settings and the
  audit page, for `admin`, `manager`, `tehran` and `east`) finished without

Decided (M5 — natural-language interface, 2026-10-19):

(Maintained reference: [docs/nl-interface.md](docs/nl-interface.md).)

- Package `bi_admin.nl`; entry point `pipeline.ask(question, request, previous=,
  today=, provider=, use_cache=, rate_limit=)` → `Answer` (`status` ok |
  clarification | invalid, `spec`, `interpretation`, `clarification`,
  `suggestions`, `warnings`, `period`, `provider`, `attempts`, `cached`,
  `log_id`). Pipeline as §5.1, with three refinements: (1) **retrieval is
  lexical**, not embeddings — phrase matching over keys/labels/synonyms (Persian
  plural/ezafe suffixes and ZWNJ tolerated), character trigrams and
  transliteration keys; no vector store or embedding service is needed, and
  `GOZAR["NL"]["RETRIEVER"]` can swap in one (pgvector stays the M7 option).
  It ranks semantic models (`MAX_MODELS` 3) and keeps `TOP_K` (20) items each,
  always the default time dimension and every item of the spec being refined;
  (2) value matching runs **after** the model, on the server, so the model never
  sees stored values; (3) a provider may answer "clarification" at any time and
  value matching may turn an answer into one.
- **What the model sees** (`nl.prompt`): instructions, `TODAY` in both calendars
  (ISO + Jalali `1405/07/26` + month name), the user's language and calendar,
  the period grammar, the retrieved catalog subset in both languages (keys,
  labels, synonyms, descriptions, types, formats, declared choices), up to 8
  few-shot examples (`Semantic.nl_examples`, only those whose keys the user may
  see), and for refinement `PREVIOUS SPEC` + the follow-up. Only metadata and the
  user's words: category values of the previous spec (non-choice category/geo
  dimensions) are **redacted to placeholders** `@v1…` and restored afterwards;
  choices, dates and numbers stay (they aren't row data). Tests assert that no
  city, province, customer name, phone or amount from the database appears in
  any prompt, for the stub and for a real HTTP round trip.
- **The model never does date arithmetic**: relative periods are names resolved
  by `calendar.periods` in the user's calendar (the spec's `calendar` stays null
  unless the user names one); explicit dates are copied as written and
  normalised to ISO by code; a whole year/month may be written `1404`,
  `1404/03`, `2025-03` and is expanded by `nl.dates` (Jalali leap years
  included).
- **Validation and retries**: each output is parsed (code fences and chatter
  tolerated), cleaned (dates), validated as `ReportSpec` (pydantic errors become
  `schema_error`s) and with the report validator *under the user's permissions*
  (`prepare`: model permission, visibility). Errors go back to the model as the
  assistant/user turns of the same conversation; `MAX_RETRIES` (2) extra calls,
  then `status: invalid` with the errors. Non-JSON output is `output_not_json`.
- **Value matching** (`nl.values`): a value index per category/geo dimension and
  user — choices (both languages) for choice fields, the related objects of the
  target's *scoped* queryset for paths ending on a relation, the related table's
  column in the user's scope for paths through relations (so "Rasht" matches
  even with no orders yet), otherwise distinct values of the scoped semantic
  queryset — capped at `VALUE_INDEX_MAX` (5 000) and cached like report results
  (scope fingerprint + data versions, `VALUE_INDEX_TIMEOUT`). Matching: exact
  after normalisation (Arabic ي/ك/ة…, Persian/Arabic digits, ZWNJ, diacritics,
  case), then a cross-script consonant-skeleton transliteration key (every
  reading of و/ی, word order free: «خراسان رضوی» = *Razavi Khorasan*), then
  fuzzy (≥ 0.8 and clearly ahead of the runner-up, reported as a warning). A
  value that only exists in another category dimension moves there (warning);
  an unknown one becomes a clarification with up to five *in-scope*
  suggestions, each with a ready-made follow-up question. Out-of-scope values
  are indistinguishable from nonexistent ones.
- **Providers** (`nl.providers`): `OpenAICompatibleProvider` (stdlib `urllib`, no
  new dependency; `POST {BASE_URL}/chat/completions`, `response_format`
  `json_schema` with the retrieved model names as an enum → automatic fallback to
  `json_object` on a 400, or `none`; `TEMPERATURE` 0), `HeuristicProvider`
  (offline, deterministic, English + Persian) and `StubProvider` (tests; builds
  the real prompt so tests can inspect it). Configuration: `GOZAR["NL"]` key →
  `GOZAR_NL_<KEY>` environment variable → default; `PROVIDER = "auto"` picks the
  LLM when `BASE_URL` and `MODEL` are set, else the heuristic. **The API key is
  read only from the environment** (`API_KEY_ENV`, default `GOZAR_NL_API_KEY`);
  a literal key in settings is system check error `bi_admin.E003`, a bad
  `RESPONSE_FORMAT` `E004`. `describe()` exposes name, model and host, never the
  key. An unreachable model falls back to the heuristic with a warning
  (`FALLBACK`, default on) or answers `502 provider_*`.
- **Heuristic interpreter** (`nl.heuristic`): recognises, in order, explicit
  dates/years/months (Jalali and Gregorian month names; ambiguous ones like
  *may*/«تیر» need a year or preposition), relative periods ("last 3 months",
  «سه ماه گذشته», «امسال», «پارسال», "year to date"…), number comparisons with
  multipliers («بالای ۵۰ میلیون», "between 2 and 10 million"), top/bottom N and
  sort order («۵ شهر برتر», «پرفروش‌ترین», "which … most" → limit 1), grain and
  chart words, then catalog phrases (longest match; a span may mean a measure
  or a dimension — "top customers" vs "customers"), then category values via
  the server-side index (it is local, so it may), negations («به جز», "except")
  and qualifiers ("revenue *from orders* over…"). An unknown word right after a
  category dimension's name is treated as a value (so «شهر نیویورک» asks
  "no City matches"); other unused words are reported as a warning ("Not used:
  …"), so a misreading is visible. Follow-ups merge into the previous spec: new

  time series → line, one group-by → bar, none → kpi, else table. It asks when

Decided (M6 — dashboards and scheduling, 2026-10-20):

- **Comparison periods** (`ReportSpec.compare_to`, `calendar.periods.comparison`,
  `engine.runner`). The validator resolves the comparison when the report has a
  bounded period: the relative period, else the first `between` (or single-day
  `eq`) filter on the time dimension; otherwise `422 compare_needs_period`.
  `previous_period`: a relative period moves by its own length in its own units
  (`last_3_months` → the 3 months before; `this_month` to date → the previous
  month up to the same day; `past_30_days` → the 30 days before); a custom range
  of whole months moves by that many months, any other range by its length in
  days. `same_period_last_year`: 12 months back in the report's calendar, except
  weekly periods (52 weeks, so weekdays line up). Month shifts clamp the day to
  the target month (31 Mehr − 1 month = 30 Shahrivar, 29 Feb + 12 months = 28
  Feb) and a range ending on a month boundary keeps ending on one (Esfand 1404,
  29 days, a year back is Esfand 1403 with its 30th) — `Offset.shift_range`.
  Execution: a second query — the same compiled report over the comparison range
  (period or the replaced range filter), unsorted, up to `REPORT_MAX_ROWS` — in
  the same reporting/timeout context; its rows are merged by group values with
  every time bucket mapped onto the current bucket it lines up with
  (`Comparison.to_current`: month/season/year grains by the month offset; day
  grain by the calendar date; week grain by the offset rounded to whole weeks, so
  weeks map one-to-one). A collision (a clamped day: 28 and 29 Feb 2024 both
  before 28 Feb 2025) keeps the exact match. It is a left join: groups that only
  exist in the comparison period are dropped. Each measure gets
  `<m>__compare`, `<m>__change` (current − previous) and `<m>__change_pct`
  (change / |previous|, `null` when previous is 0 or missing) and columns with
  `role: "comparison"`, `measure`, `comparison` (compare/change/change_pct),
  labels in both languages; the response has `compare_to` and `comparison`
  (kind and range, with Jalali dates). Cached with the report (the spec carries
  `compare_to`); exported like measures. Drill-down accepts `comparison: true`
  and moves the cell's buckets to the comparison bucket (`to_comparison`). The
  interpretation sentence says "compared with the previous period (…)". Sorting by
  a comparison column (e.g. "biggest movers") is not supported.
- **Saved reports** (`bi_admin.SavedReport`, abstract `Shared`): owner, name,
  description, `semantic_model`, the spec as submitted with defaults dropped (a
  `null` calendar stays null, so every viewer gets their own), and sharing —
  `visibility` private | users (M2M users and groups) | everyone. Sharing rules
  (`bi_admin.sharing`): listed for the owner, the shared users/groups or everyone,
  *and only when the viewer may report on its semantic model*; anyone who can
  open it may duplicate it (a private copy); only the owner changes or deletes
  it (`403`); someone else's private report is a `404` like a missing one;
  shares go to active staff only. Saving validates the spec for the owner
  (`prepare`: `403`/`422`). Nothing about running changes: the SPA runs the
  stored spec through `/reports/run`, so the viewer's permissions, visibility and
  row rules apply (a spec using a measure hidden from the viewer lists as
  `available: false` with the reason, and running it is the usual `422`).
  The model has no Django permissions (`default_permissions = ()`): access is
  ownership + sharing + the model permission. API `/api/saved-reports`
  (list `?q=&mine=`, create, get, patch, delete, `POST /{id}/duplicate?name=`),
  `/api/sharing/targets?q=` (users and groups to pick). SPA: `/reports?saved=<id>`
  (the URL spec still wins; "edited" marker, Save / Save as / Rename & share /
  Duplicate / Delete / Email schedule / Add to dashboard), **Saved reports** page,
  and **Save report…** on an Ask answer.
- **Dashboards** (`bi_admin.Dashboard` + `DashboardWidget`): sharing as above,
  but a dashboard is listed when the viewer may report on at least one widget's
  model. A widget is a saved report (FK, `SET_NULL` — the tile then says it was
  deleted) or an inline spec, plus title, chart and a place on a 12-column grid
  (`x, y, w, h`; validated to fit). A saved-report widget is shown to a viewer
  who may open that report *or* when the dashboard's owner owns it (putting your
  own report on your shared dashboard shares it); a third person's report that
  isn't shared with the viewer shows "not shared with you", and an editor can
  only add reports they can open. Duplicating keeps saved-report widgets the new
  owner can open and inlines the rest. Editing replaces all widgets in one
  `PATCH` (owner only). `filters` stores the offered category filters
  (`dimensions`) and defaults (`period` or `range`, `values`). **Global
  filters** (`bi_admin.dashboards.apply_filters`) apply per widget, matched by
  dimension key *as the viewer sees the model* (a hidden dimension doesn't
  match): the period replaces the widget's relative period and any range
  filter on its time dimension (a comparison stays, now against the new
  period); a category filter replaces the widget's own filter on that key
  (`eq`, or `in` for several values). Widgets without the field report it as
  `ignored` and the tile says "Not filtered by …". `POST
  /api/dashboards/{id}/resolve {filters}` returns every widget's effective spec;
  the SPA runs them in parallel through `/reports/run` (cache, background jobs,
  limits and audit as for any report), and each tile has drill-down and export.
  Filters can never widen access: a city outside the viewer's scope just yields
  no rows. SPA: **Dashboards** list (create, pin, duplicate, delete) and
  `/dashboards/<id>`: filter bar (period presets or a date range, value pickers
  per offered dimension), the grid (react-grid-layout 2.3, new dependency;
  mirrored for RTL, items anchored left because absolutely positioned boxes
  otherwise start at the right edge in RTL; one column in reading order below
  720 px), and the owner's editor (drag by the handle, resize by the corner,
  add/edit widget from a saved report or a builder in a dialog, offered filters
  and defaults). **Pin as home page** stores `options.home_dashboard` in the
  user's preferences (validated as an id); the home page then shows that
  dashboard, with the Ask panel folded below it.
- **Scheduled e-mail** (`bi_admin.Schedule`, `bi_admin.scheduling`): owner, name,
  target (a saved report *or* a dashboard — a check constraint), frequency daily
  | weekly (weekday, Monday = 0) | monthly (day 1–31, clamped to the month's
  length, in the Gregorian or Jalali calendar), local time, IANA time zone
  (default: the owner's new **Settings → Time zone** preference,
  `options.timezone`, else `TIME_ZONE`), recipients (M2M users), attachment
  csv | xlsx | none, enabled, `next_run_at` (UTC, indexed) and `last_run_at`.
  `compute_next` walks local days to the first matching day whose local time is
  strictly after now (DST-safe through `zoneinfo`). Recipients must be active
  staff users who can open the target and have an e-mail address (`400` with the
  usernames otherwise); only the owner sees or changes a schedule. Sending
  (`send_due(now)`): every enabled schedule with `next_run_at <= now` is claimed
  by a conditional `UPDATE … WHERE next_run_at = <read value>` that moves it to
  its next future run (two senders never send twice; a schedule missed for a while
  is sent once), then `deliver()` builds one e-mail **per recipient, as that
  recipient** (`JobRequest` with their language and calendar): each report runs
  through `run(kind="email")`, so permissions, visibility, row rules, limits and
  the cache apply, and the run is audited (`ReportLog.Kind.EMAIL`, user = the
  recipient). Dashboards use their stored default filters. The HTML e-mail
  (`bi_admin/email/scheduled_report.html` + a text part) has a section per report
  with the interpretation sentence, KPI cards (value, ▲/▼ change %, previous
  value) or a table (first `EMAIL_MAX_ROWS` = 50 rows; the attachment has all),
  formatted on the server by `bi_admin.formatting` like the SPA (measure
  formats, Jalali/Gregorian bucket names, Persian digits and separators,
  RTL for `fa`); the subject and dates are in the recipient's language and
  calendar. Attachments come from `engine.export` (headers in the recipient's
  language, RTL sheet for `fa`), one per non-empty section. Recipients who can no
  longer open the target, have no address or are inactive are skipped; a
  sending error fails only that recipient. Every e-mail is a
  `bi_admin.ScheduleDelivery` row (schedule, recipient, address, status
  sent | failed | skipped, trigger schedule | manual, language, calendar,
  report and attachment counts, error, duration), readable with
  `view_reportlog` at `GET /api/audit/deliveries` and **Audit log → Email
  deliveries**; the owner sees the latest 20 per schedule. Runners:
  `manage.py gozar_send_schedules` (cron; `--dry-run`, `--schedule ID` to send
  one now) and `gozar_worker` (every 30 s unless `WORKER_SENDS_SCHEDULES` is
  off); the API's `POST /schedules/{id}/send[?only_me=true]` sends at once
  without touching the timetable. Uses Django's e-mail framework
  (`GOZAR["EMAIL_FROM"]` or `DEFAULT_FROM_EMAIL`); `GOZAR["BASE_URL"]` adds an
  "Open in Gozar" link. The demo writes e-mails to `example_project/.mail` with
  the file backend.
- **NL**: the heuristic recognises a comparison cue followed by what to compare
  with — "compared to/with", "vs", "versus", "against", «نسبت به», «در مقایسه
  با», «با … مقایسه کن» + "last/previous <unit>", «<unit> قبل/گذشته», «پارسال»,
  "the previous period", «دوره قبل», "the same period last year", «دوره/مدت
  مشابه سال قبل», and "year over year", "month over month"… — before the time
  parser, so "last year" there isn't read as the report's period. A year means
  `same_period_last_year`, another unit `previous_period`; without a period the
  question compares the current unit to date ("revenue vs last month" →
  `this_month` vs the previous one; "compared to last year" → `this_year`); "the
  previous period" with no period asks which. Follow-ups add or drop it
  ("compare with last year", «با پارسال مقایسه کن», "without comparison"). The
  LLM prompt explains `compare_to`; the evaluator compares it in the semantic
  view; the golden set has 18 more cases (198; the heuristic still scores 1.0).

  `fk_name`, `name` (payload key, default the reverse accessor, e.g. `items`),
  fields/exclude/readonly/widgets as above, `extra` (3), `min_num`, `max_num`,
  `can_delete`, `show_change_link`, `ordering`, `get_queryset`. A save sends
  `"__inlines__": {"items": [{"pk": …|null, "values": {…}, "delete": bool}]}`
  (`__` can't clash with a field name). The server builds a Django
  `inlineformset_factory` formset over **every visible row** of the parent —
  submitted values merged over the stored ones, new rows over the model's
  defaults (also sent to the SPA as `defaults`), rows left out unchanged — so
  `min_num`/`max_num`, cross-row unique checks and `has_changed()` behave as in
  admin; untouched extra rows are skipped. The parent form and every formset are
  validated before anything is written; then parent, many-to-many and inlines
  save in one transaction. Errors: `inline_errors: {name: {rows: {"<index>":
  {field: [msg]}}, non_form: [msg]}}`. Permissions are the inline model's
  (view, add for new rows, change for changed rows, delete; an auto-created
  through model follows the parent's change permission); a missing permission
  is a row error, no view permission hides the inline (403 when submitted).
  **Scope**: an inline lists only rows of its model the user may see (`hidden`
  counts the rest, which saving never touches; a hidden pk can't be addressed),
  relation fields only accept rows in scope, deletions run the normal deletion
  plan, and a saved row that ends up outside the scope rolls the whole save back
  (`403 out_of_scope`). The change log gets one entry on the parent with an
  `inlines` summary (added, changed with diffs, deleted) plus an entry per row.

  `{"name", "filename", "url"}` it was read as — keeps the file, `null` clears
  it (an error for a required one), a part replaces it; Django's form fields

  storage stores (`STORAGES["default"]`). `UPLOAD_MAX_BYTES` (10 MB) per file.

  (or a copied inline row's) own file, so a payload can't point at arbitrary
  storage paths.

Decided (M7 — scale, 2026-10-20):

- Package `bi_admin.scale`: `PreAggregation` (declarations), `additive` (measure
  decomposition), `matcher`, `planner`, `refresh`, `state` (freshness and change
  records), `scope` (row-level scope carried over), `columnar` (the backend
  interface) and `columnar.duckdb`. One state model, `bi_admin.Materialization`
  (kind preaggregation | columnar, name, definition hash, current table and
  generation, status, rows, size, build/refresh times and mode, captured source
  data versions and the models read, `stale_since`, change records
  `dirty_from`/`dirty_to`/`needs_rebuild`/`changes`, hits, last error, a build
  lease, details); no Django permissions — the System page's
  `bi_admin.view_system` governs it.
- **Declaration**: `Semantic.pre_aggregations = [PreAggregation(name,
  measures=[…], dimensions=[…], time_dimension=None (the model's), time_grain="day"
  (None: no time column; a model without a time dimension gets none),
  calendar=None, scope_fields=[…], refresh_every, rebuild_every,
  incremental_window, max_staleness, label, description)]`, bound (and checked)
  with the semantic model, so mistakes are `ImproperlyConfigured` → system check
  `bi_admin.E001`. Refused at binding, because the result could not be exact:
  distinct counts (no approximate opt-in — a HyperLogLog sketch would be a new,
  explicitly approximate measure type; deferred), aggregates other than
  Sum/Count/Avg/Min/Max, floating-point sums and averages, any dimension,
  measure (its `filter=` included) or scope field reading across a to-many
  relation (a summary row would count a base row more than once), time
  dimensions other than the bucketed one, and coarse grains with an unknown
  calendar (default `DEFAULT_CALENDAR`).
- **Additive parts** (`additive.decompose`): each aggregate leaf of a measure
  expression becomes stored parts and a re-aggregation — `Sum` → `Sum(part)`;
  `Count` → `Coalesce(Sum(part), 0)`; `Avg` → `Sum(s) / NULLIF(Sum(c), 0)`;
  `Min`/`Max` → `Min`/`Max` of the part; `default=` → `Coalesce`. Arithmetic
  around the leaves (`Sum(a) / Count(b)`, `Coalesce(…)`) is kept. Identical parts
  of different measures share a column (revenue's sum is the average's
  numerator). **Exactness** is by construction and verified by tests: every
  re-aggregation keeps the original leaf's output field (same Django converters),
  part columns keep the source's decimal places (38 digits, sums grow), and the
  average divides the way the database's own `AVG` does — PostgreSQL
  `numeric / numeric` (which is what `AVG(numeric)` computes, same scale rules),
  SQLite `CAST(sum AS REAL) / count` (its `avg()` divides the exact integer sum
  as a double).
- **Storage**: one table per pre-aggregation, `gozar_pa_<semantic>_<name>_<hash8>_<generation>`,
  created with Django's schema editor from an unmanaged model in Gozar's own app
  registry (migrations, checks, discovery and signals never see it; the DDL is
  collected and executed directly because the SQLite schema editor refuses to run
  inside a transaction). The hash covers everything the rows depend on (model,
  table, base queryset, `TIME_ZONE`, grain and calendar, column definitions,
  part expressions), so a changed definition is never read before it is rebuilt.
  Columns: `t_bucket` (the bucket's start date, indexed), `d_<key>` per
  dimension, `s_<i>` per scope field, `m_<i>` per part; all nullable, typed from
  the source field (relations as their key). A rebuild fills a new generation with
  one `INSERT … SELECT` of the grouped ORM query (`compiler.as_sql()`, columns
  from `compiler.select`, values as parameters), switches the state row to it and
  drops the previous table and orphans; readers that raced a drop fall back to
  the ORM (a savepoint around the attempt). `PREAGG_DATABASE` ("default") is
  where tables are written; they are read on `REPORTS_DATABASE` (a replica gets
  them by replication).
- **Matching** (`matcher.find`, for the report and its comparison report
  together): every measure stored; every group-by a stored dimension or the time
  dimension at a grain its buckets nest in (`Grain.serves`: day buckets serve
  every grain in both calendars; month → season → year within one calendar; weeks
  only weeks; a Jalali month never answers a Gregorian one); every filter on a
  stored dimension or the time dimension; every date range — filters (`eq`,
  `in` per day), the relative period, the comparison period — on bucket
  boundaries (`aligned`); scope translatable; built from the current definition;
  fresh or stale within `max_staleness`. The smallest match (rows) wins. Refusals
  are reported with codes: `measure_not_included`, `dimension_not_included`,
  `filter_not_included`, `time_dimension_not_included`, `grain_not_compatible`,
  `range_not_aligned`, `not_built`, `definition_changed`, `stale`,
  `custom_queryset`, `scope_not_covered`, `scope_expression`, `scope_to_many`,
  `scope_lookup`, `scope_value`. **Retargeting** instead of a second compiler:
  the validated report is copied onto a shadow semantic model whose dimensions are
  the summary columns (the time dimension becomes the `t_bucket` date, so grains
  are `Trunc` of it or the `CalendarDay` lookup) and whose measures are the
  re-aggregations; `compile_report(…, source=)` then builds it exactly like the
  ORM path — grouping, null buckets, Jalali boundaries, filters, default and
  explicit sorting with group-key tie-breakers, `LIMIT`, the calendar check.
- **Row-level scope** (`scope`): a pre-aggregation is built from
  `Semantic.get_queryset(None)` (trusted rows). It answers a user only when their
  `get_queryset(request)` selects the same rows (`scope_key` equal; else
  `custom_queryset`) and every condition of their combined rule `Q` reads a stored
  path — a dimension or a `scope_fields` column — with a plain value (instances →
  keys, querysets → subqueries); `Q(pk__in=[])` (deny all) needs no column.
  Connectors and negation are kept, so Django generates the same null-aware SQL.
  Anything else refuses (never "ignores"): unscoped totals are never served to a
  scoped user. Superusers bypass rules as before. The demo stores
  `customer__city__name_en` in `daily_sales` (regional users are served from it)
  but not in `monthly_status` (they get `daily_sales` or the ORM instead).
- **Freshness** (`state`): a build captures the data versions (the result
  cache's, §M4) of every model its SQL reads *before* reading them; the copy is
  fresh while they are unchanged. Stale copies answer only within `max_staleness`
  (`PREAGG_MAX_STALENESS`, default 0 = never), are flagged in the response
  (`stale`, `stale_since`, `lag_seconds`) and their rows are never put in the
  result cache. **Change records** hook into the data-version mechanism
  (`cache.listeners`): a saved/deleted row of the pre-aggregation's own model
  widens `dirty_from`/`dirty_to` by its local date — old and new (a `pre_save`
  reads the stored time when the row exists and the field may change, only for
  models with incremental pre-aggregations); a related model, `cache.bump()` (bulk
  writes) or `bump_all()` sets `needs_rebuild`. Records are written by
  `on_commit` (one conditional `UPDATE` with `LEAST`/`GREATEST`, no lost updates,
  nothing for rolled-back writes, no lock held inside the writer's transaction);
  stale without records (a rollback, an evicted version, a write that only bumped)
  means a full rebuild. Writes Django doesn't see (raw SQL) are as invisible as
  they are to the result cache: call `bump()`.
- **Refresh** (`refresh`): `rebuild`, or `incremental` (declared
  `incremental_window` days back from today, widened to the recorded dirty
  range and to whole buckets, plus the null bucket: delete and re-insert in one
  transaction); `auto` picks incremental when declared and safe. A build lease on
  the state row (`PREAGG_BUILD_LEASE_SECONDS`) keeps builders apart (`BuildBusy`);
  records that arrive during a refresh are kept. Failures are recorded
  (`last_error`, status failed when there is no table) and not retried before
  `refresh_every`. **Schedule** (`refresh.due`): not built, definition changed or
  `rebuild_every` (`PREAGG_REBUILD_EVERY`, a day) elapsed → rebuild; stale and
  `refresh_every` (`PREAGG_REFRESH_EVERY`, 10 min; the demo uses 1 min) since the
  last refresh → auto. `gozar_worker` runs due refreshes and syncs every 30 s
  (`WORKER_REFRESHES`); `manage.py gozar_preaggregate [names] [--rebuild |
  --incremental | --due | --list] [--drop-orphans]` does it by hand. Calendar
  coverage is checked at build time for Jalali coarse grains (`409
  calendar_not_populated`, like reports).
- **Planner** (`planner.execute`, called by `run()` after validation, the cache
  lookup and the audit entry are set up): a matching pre-aggregation, else the
  semantic model's columnar engine, else the ORM; `PREAGGREGATIONS = False` turns
  the first off. `run(..., engine="orm" | "preaggregation" | "duckdb")` forces one
  (no cache; `409 engine_unavailable` with the refusals) — for tests and the
  benchmark, not exposed in the API. The response gets `execution: {engine,
  pre_aggregation, stale, stale_since, lag_seconds, considered: [{engine, code,
  detail, pre_aggregation}]}`; `ReportLog` gets `engine` and `pre_aggregation`
  (for a cache hit: the engine that computed the cached rows, which the cache
  entry keeps). Cache keys are unchanged (the ORM-compiled SQL's dependencies):
  every engine's fresh result is the same rows. Hits are counted per
  pre-aggregation/copy when it actually answers (not for cache hits).
- **Columnar engine** (`columnar`): `Semantic.engine = "duckdb"`, overridden by
  `GOZAR["SEMANTIC_ENGINES"] = {"order_metrics": "duckdb"}`; backends by name in
  `COLUMNAR_BACKENDS`; `ColumnarBackend` = `available()`, `synced_labels()`,
  `sync()`, `execute(reports, request)` → rows per report or `Unsupported(code)`,
  `status()`, `sync_every()`. A ClickHouse backend would implement exactly these
  (and live in `COLUMNAR_BACKENDS`); none ships.
- **DuckDB** (`columnar.duckdb`, extra `gozar[duckdb]`, settings
  `GOZAR["DUCKDB"]`: `PATH`, `MAX_STALENESS` 0, `SYNC_EVERY` 600, `THREADS`,
  `MEMORY_LIMIT`). *Sync* copies the tables the models using it read (their own
  model, every model a dimension or measure joins to through to-one relations,
  `CalendarDay`) from the reports database, all concrete columns, plus
  `<column>__ld` for datetime columns — the local date computed by the primary
  database with the ORM's own `TruncDate`, so day boundaries and time zones are
  identical by construction. Text dimensions get **rank tables** (distinct values
  in the primary database's `ORDER BY` order): DuckDB compares bytes, PostgreSQL's
  `en_US` collation does not ("Ali Z" vs "Alia", "پ" vs "ت", "É" vs "e"), and a
  test proves the sort differs without them. Rows stream through a CSV file into
  `COPY` (~140× faster than parameterised inserts without pyarrow/pandas;
  quoting, `\N` nulls with `allow_quoted_nulls = false`) into a new file that
  replaces the old one atomically (`os.replace`; readers reopen when the file's
  identity changes; one sync at a time via the lease). The file stores the
  captured versions, models, vendor and time zone, and refuses to answer for
  another database or zone. *Queries* are generated from the validated spec only:
  identifiers from model metadata (quoted), every value a `?` parameter, joins
  along to-one paths (`LEFT` for nullable keys, as Django), filters on local
  dates, negations as `(…) IS NOT TRUE` (Django's null-aware `exclude`),
  `icontains` as the primary database does it (SQLite folds ASCII letters only;
  PostgreSQL `upper()`), Gregorian buckets with `date_trunc` (ISO weeks, quarters
  as seasons), Jalali ones from the synced calendar, `NULLS LAST`, the same
  default sort and tie-breakers, `LIMIT limit + 1`, the same `409
  calendar_not_populated` payload, and the statement timeout through
  `connection.interrupt()` → `504`. Measures: single aggregates (`Sum`, `Count`
  incl. **distinct** — exact here, unlike pre-aggregations —, `Avg`, `Min`/`Max`
  of numbers, with `filter=`, over fields or `+ - *` of fields; `Coalesce(agg,
  constant)`), values converted as the primary database and Django return them
  (`columnar.numbers`: SQLite's 15-digit `Decimal` context for decimal
  aggregates; PostgreSQL's `numeric_div` scale rules reproduced exactly for
  averages — 3 000 random cases matched PostgreSQL 16 digit for digit, and the
  PostgreSQL test run checks 400 more). Other
  measures, expression dimensions, a custom `get_queryset`, and row rules that
  can't be translated (expressions, to-many paths, lookups beyond
  exact/in/comparisons/range/isnull) raise `Unsupported` → ORM. Query values from
  queryset-valued rules are evaluated on the primary database first.

- **Rule**: everything that renders user-generated or data-driven text isolates
  it, so English inside Persian pages and Persian inside English ones both read
  correctly; numbers, dates and identifiers stay LTR. SPA helpers in
  `frontend/src/bidi.tsx`: `<bdi>` for inline text, `<UserText>` for blocks
  (`dir="auto"` + `.user-text`: `unicode-bidi: plaintext; text-align: start;
  white-space: pre-line`), `isolate()` (FSI…PDI) for strings that leave the DOM's
  bidi handling — ECharts canvas labels, legends and tooltips (`reports/Chart.tsx`,
  `system/BarChart.tsx`), `title=` tooltips, `<option>` text. `t()` isolates every
  string parameter, so toasts, `confirm()` prompts and messages that quote a name
  are safe by default (a value that is *sent* to the API is built with the raw
  `translate()`, and the server strips isolate marks from stored names anyway).
  CSS gives `p/div/li/dd/td/h1–h4[dir="auto"]` and `input/textarea[dir="auto"]`
  `unicode-bidi: plaintext; text-align: start`. Descriptions on the dashboard and
  report pages are their own paragraph now, not part of the owner line.
- **Lint**: `npm run lint:bidi` (`frontend/scripts/check-bidi.mjs`, run first by
  `npm run build`, hence in CI) flags a JSX child that renders a name, title,
  description, label, question, problem, `personName()`, `fmt.cell()` or
  `dimensionText()` value outside `<bdi>`, `<UserText>`, an element with `dir=`,
  or `isolate()`; a deliberate exception takes a `bidi-ok` comment. It is a
  line-based heuristic (no TypeScript parser: TypeScript 7 has no JS compiler
  API), cheap enough to keep new code honest. No frontend unit-test runner was
  added for it.
- **E-mails**: titles, descriptions and section titles are `dir="auto"` blocks
  (plaintext, start-aligned); table cells and KPI labels are `<span dir="auto">`
  so a column keeps the page's alignment; KPI values and changes are
  `dir="ltr"` (the sign stays with the number). The subject isolates the name
  when its direction differs from the recipient's language or it mixes both
  (`formatting.isolate(text, lang)`).
- **Translatable content** (`bi_admin.translations`, abstract `Translatable`):
  `SavedReport`/`Dashboard` (`Shared`) and `Schedule` have `name_i18n` and
  `description_i18n`, `DashboardWidget` `title_i18n` — JSON `{language: text}`
  over the configured languages (`LANGUAGE_CHOICES`). `Schedule` gained a
  `description` (shown in the schedule list and as a note in its e-mail). The
  plain field stays the default language's text (`GOZAR["DEFAULT_LANGUAGE"]`) —
  ordering, `__str__`, old clients — and `Translatable.save()` keeps the two in
  step: a plain field changed directly becomes the default language's text; a
  blank one shows the default language, else the first language there is
  (without inventing a translation). `bulk_create` callers sync by hand.
- **Resolution**: the viewer's language → the default language → the plain field
  → any language (`translations.pick`). API payloads give `name`/`description`
  (`title` for widgets, `saved_report.name`, a schedule's `target.name`) in the
  viewer's language plus `*_i18n` with every stored language for editing; a
  widget's `title_i18n` is its own (empty: it shows its report's name, per
  language). Writes accept `name_i18n`/`description_i18n`/`title_i18n` (they
  replace the stored languages; unknown languages are refused, empty texts
  dropped) and still the plain fields (the default language only). Duplicates
  translate "Copy of …" into each language.
- **Search**: the saved-report and dashboard lists' `q` matches the plain fields
  and each language's key (`name_i18n__fa__icontains`): JSON is stored with
  `\u` escapes, so matching the whole document would miss Persian text.
- **Exports**: `POST /reports/export` and `GET /reports/jobs/{id}/export` take
  `title` (the SPA sends the saved report's or widget's name): it names the file
  (`slugify(…, allow_unicode=True)`, RFC 6266 `filename*=` for non-ASCII) and the
  XLSX sheet. E-mail attachments use the section title the same way.
- **E-mails** are built per recipient inside their language, so the subject,
  title, description, schedule note and every section title are theirs.
- **SPA editing**: `components/TranslatedInput` — one field per configured
  language, the default first and marked; with one language it is a plain field.
  Used by the name/description dialog of saved reports and dashboards, the widget
  dialog and the schedule dialog. The session carries the languages and the
  default (`/auth/me` preferences).
- **Migrations**: `0010_translations` (fields) and `0011_translations_data`
  (copies existing names, descriptions and widget titles into the default
  language's key; nothing to undo backwards).
- **Demo**: `seed_demo` gives the saved reports, the *Sales overview* dashboard,
  its *Orders by status* widget and the weekly e-mail Persian names and
  descriptions; `seed_demo --content-only` refreshes just that content in a
  seeded database (orders, customers and users untouched).
- Checked (2026-10-21) with Playwright on a copy of the demo database: the
  Persian dashboard with an English name and description (*Sales overview (Q4,
  v2)*), the English dashboard with Persian ones, and the HTML e-mail in both

Decided (alerts to Telegram, 2026-10-21):

- Package `bi_admin.alerts`; settings `GOZAR["ALERTS"]` (`alerts/conf.py`, every key
  in the README). Models: `Alert` (source, key, severity info | warning | error |
  critical, kind alert | resolved, scrubbed title/message/details, language,
  release, `repeats`, `suppressed_before`, delivery pending | deferred | sent |
  failed | muted | below_threshold | no_channel, acknowledgement with user and
  channel), `AlertState` (one row per key: firing, severity, last alert, last
  delivery, held-back count, `notified`, `muted_until`), `AlertDelivery` (the
  outbox: one row per alert and recipient, lease, attempts, `next_attempt_at`),
  `AlertSource` (System page overrides) and `WorkerHeartbeat`. No Django
  permissions: `bi_admin.view_system` governs all of it, including the switches.
  Migration `0012_alerts`.
- **Pipeline** (`alerts.pipeline`): `raise_alert(source, key, severity, title,
  message, details)` and `resolve(source, key)` never raise (a re-entrancy guard
  drops alerts raised while recording one) and write to `default` only. The key
  is `<source>:<key>`; the state row is locked (`select_for_update`) so concurrent
  processes agree. Within the source's window after an alert row was created, a
  repeat that isn't more severe bumps that row's `repeats` and the held-back
  counter instead of adding a row; the next row after the window carries the
  count, which its message states ("2 more alerts like this were held back").
  Escalation (higher severity) breaks through. Below the source's minimum
  severity, muted, or without a channel, the alert is recorded but not queued.
  In quiet hours (`QUIET_HOURS`, may wrap midnight, `QUIET_HOURS_TIMEZONE`)
  anything below critical is queued for the end of them. `resolve` writes a
  resolved notice only for a firing key, delivered only if the episode was
  delivered; it keeps the condition's severity. Event sources (exceptions, job
  failures) simply never resolve.
- **Sending never happens in a request**: the pipeline inserts outbox rows;
  `gozar_worker` sends them every 5 s (`outbox.deliver_due`): conditional-UPDATE
  claim with a lease, render, `sendMessage`; transient errors (network, 5xx, 429
  with `retry_after`) retry with `RETRY_BACKOFF` doubling up to
  `RETRY_BACKOFF_MAX` until `MAX_ATTEMPTS`; permanent ones (400/401/403/404, an id
  outside the allow-list, channel off) fail at once; rows stuck in `sending` are
  retried after `DELIVERY_LEASE_SECONDS`. Failures are logged (token removed) and
  never raised. Caveat: an alert raised inside a transaction that later rolls
  back is lost with it (the 500 handler runs after `ATOMIC_REQUESTS` ends, so it
  isn't affected).
- **Telegram** (`alerts.telegram`, stdlib `urllib`, no new dependency): the token
  is read only from the variable named by `TOKEN_ENV` (`GOZAR_TELEGRAM_BOT_TOKEN`),
  never stored, logged, returned or shown — the API says `token_configured` and
  the variable's name; a literal `TOKEN` in settings is check error
  `bi_admin.E006`. `ALLOWED_CHAT_IDS` (a list or a comma/space string, falling
  back to `GOZAR_TELEGRAM_ALLOWED_CHAT_IDS`) must be non-empty and all numeric,
  otherwise the channel stays off with `problems` (check warning
  `bi_admin.W002`, a warning on the System page); `ENABLED` None = on when both
  are set, True = required, False = off. `Client.send` refuses any id outside
  the list before any HTTP call, whatever the outbox row says; the API returns
  only the number of ids. Messages use HTML parse mode with everything escaped,
  in `LANGUAGE` (en | fa; Persian lines start with RLM, inserted values are
  FSI…PDI isolated, Persian digits), cut to 4 096 characters (traceback first),
  and link to `<BASE_URL>/system?alert=<id>` when `GOZAR["BASE_URL"]` is set.
- **Interactive bot** (`alerts.bot`, `TELEGRAM["INTERACTIVE"]`): long polling
  (`getUpdates`, offset kept in an `AlertState` row) in a daemon thread of
  `gozar_worker` (`POLL_IN_WORKER`) or `manage.py gozar_telegram_poll` — no
  webhook. An update is acted on only if it is a plain `message` with text, in a
  `private` chat, with `chat.id == from.id`, `from.id` in the allow-list, not from
  a bot, not sent on behalf of a chat or via a bot, not forwarded. A sender
  outside the list (spoofed chat ids, groups, channel posts, member updates
  included) gets no reply, a log line at most once a minute with the count, and
  a `telegram` alert to the allowed users (sender id and username, never their
  text); allowed senders in other shapes are ignored and logged. Commands:
  `/status` (worker heartbeat, job counts, firing and recent alerts, outbox,
  release), `/alerts` (latest 10), `/ack <id>`, `/mute <key> <30m|2h|1d>` (capped
  at `MAX_MUTE`), `/unmute <key>`, `/help` — operational state only, never report
  data. Polling refuses to start unless the channel is enabled and interactive.
- **Sources** (`alerts.sources`; each `enabled`, `min_severity`, `window` in
  `SOURCES`, overridden from the System page): `exceptions` — `AlertHandler` on
  `django.request` (attached in `ready()` with `LOG_HANDLER`, or via `LOGGING`):
  method, path without query, route, user id (only when the auth middleware
  already loaded the user, no query), exception type and message, the last
  `TRACEBACK_FRAMES` frames (file relative to its package, line, function, source
  line — never locals), release (`RELEASE` → `GOZAR_RELEASE` → version + git sha
  read from `.git`); key = exception type + innermost project frame, or status +
  route for 5xx without an exception. `jobs` — failures with a 5xx status
  (`statement_timeout` is a warning; 403/422 are the user's, not alerts) and
  `worker_lost`. `worker` — heartbeat rows written every 15 s, marked stopped on
  a clean exit (SIGTERM is turned into one); stale past `WORKER_STALE_SECONDS` is
  an error (only once a worker has run), a crash is critical, a restart
  resolves it. A dead worker can't report itself: `manage.py gozar_alerts`
  (cron) runs the checks and sends the outbox; the System page shows the
  heartbeat. `schedules` — one alert per send with failed recipients (ids, not
  addresses), resolved by a clean send. `preaggregations`/`columnar` — refresh
  and sync failures (configuration errors included), resolved by the next
  success; stale for longer than `max(max_staleness, refresh/sync interval) +
  STALENESS_GRACE`. `nl` — `NL_ERRORS` provider errors or fallbacks within
  `NL_ERRORS_WINDOW` (a counter in the report cache), resolved when the window
  passes quietly. `checks` — `run_checks(include_deployment_checks=True)` at
  worker start and every `SYSTEM_CHECKS_EVERY`: one alert listing every error and
  warning, re-raised (after a resolved notice) when the set of ids changes.
  `database` — `DATABASE_MAX_BYTES`, `TABLE_GROWTH_PERCENT` (and
  `TABLE_GROWTH_MIN_BYTES`) between snapshots `TABLE_GROWTH_PERIOD` apart,
  `DISK_USAGE_PERCENT` per device of `DISK_PATHS` (default `MEDIA_ROOT` and the
  SQLite file's folder). `logins` — `user_login_failed` plus Gozar's own refusal
  of non-staff accounts, `FAILED_LOGINS` per IP (`REMOTE_ADDR`, or
  `CLIENT_IP_HEADER` behind a trusted proxy) within `FAILED_LOGINS_WINDOW`;
  neither username nor password is kept. `telegram` and `test` as above. The
  periodic checks run every `CHECK_EVERY` in the worker, each isolated.
- **Scrubbing** (`alerts.scrub`) applies to every title, message, detail and
  traceback line: known secret values (bot token, LLM key, `SECRET_KEY`,
  database passwords), values of secret-named keys (password, token, cookie,
  CSRF, session, authorization, API key…), bearer/basic credentials, URL
  passwords, bot tokens, JWTs, `sk-`/GitHub/Slack/AWS keys, long hex and mixed
  base64-like runs, and e-mail addresses.
- **API** (`/api/system/alerts*`, System page permission): `GET /alerts/status`,
  `GET /alerts` (filters severity, source, kind, delivery, acknowledged, `q`,
  `id`; paginated; delivery rows without their chat ids), `POST /alerts/test`
  (202; queued, the worker sends it), `POST /alerts/{id}/ack`, `PATCH
  /alerts/sources/{name} {enabled, min_severity}` (`null` resets). SPA:
  **System → Alerts** (`system/AlertsSection.tsx`): channel card with the refusal
  reasons, worker and outbox, the source table with switches and severity
  selects, recent alerts with filters, details (message, traceback, key,
  release, per-recipient delivery state) and Acknowledge; `?alert=<id>` opens
  one. All strings in en/fa.
- **Commands**: `gozar_alert_test [--message] [--severity] [--queue-only]`,
  `gozar_telegram_whoami` (getMe), `gozar_telegram_poll [--once]`,
  `gozar_alerts [--no-check] [--system-checks] [--no-deliver] [--purge]`.
  `gozar_worker` also purges alerts older than `KEEP_DAYS`.
- **Demo**: reads `GOZAR_TELEGRAM_BOT_TOKEN` and `GOZAR_TELEGRAM_ALLOWED_CHAT_IDS`
  (off when unset), `GOZAR_TELEGRAM_INTERACTIVE`, `GOZAR_ALERTS_LANGUAGE`,
  `GOZAR_ALERTS_QUIET_HOURS`. Tests fake the Bot API (`telegram._http`) and an
  autouse fixture clears the variables and fails any real call; the token and
  ids in tests are obviously fake.
